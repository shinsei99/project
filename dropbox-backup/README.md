# 社内共有フォルダのバックアップ

社内の共有フォルダ（社員全員が触る）を、**オーナーしか触らない個人Dropbox**へ週1回ミラーする。

| | |
|---|---|
| 元 | `Dropbox-大京商事　株式会社/共有フォルダ/（★必読★）新共有フォルダ` |
| 先 | `Dropbox-個人/社内バックアップ/（★必読★）新共有フォルダ` |
| 実行 | 毎週 **日曜 6:00**（launchd `com.shinsei.dropbox-backup`・**メインPCのみ**） |
| 方式 | `rsync -a --delete`（ミラー）。**50件以上消える回は1件も触らずに中断** |
| 規模 | 22,575件 / 約11GB（2026-08-31実測） |

## 使い方

```bash
bash dropbox-backup/_launchd/install-launchd.sh    # 登録（メインPCで1回だけ）
bash dropbox-backup/backup.sh                       # 手で1回走らせる
cat  dropbox-backup/last-run.txt                    # 前回の結果（1行）
ls -1t dropbox-backup/logs/ | head                  # 詳しいログ（12週ぶん）
```

## このバックアップで守れること・守れないこと

**守れる**: 社員の誰かが共有フォルダのファイルを消した・上書きした・フォルダごと動かした。
個人Dropboxは他人が触れないので、社内側の事故がそのまま伝染しない。

**守れない**:

- **ミラーなので、元で消えたファイルは次回の実行で先からも消える。**
  猶予は「気づくまで最大1週間」＋「個人Dropboxの削除履歴30日」＝実質1か月強
- **同じMac・同じDropboxアプリ経由**なので、Macの故障やDropboxアカウント事故には両方巻き込まれる。
  遠隔地・別媒体のバックアップではない

## 安全弁（なぜ入っているか）

ミラー＋`--delete` の一番怖い事故は、**Dropboxが同期していない状態で走ること**。
元が空に見えると `--delete` がバックアップを丸ごと消す。そこで:

| 仕掛け | 中身 |
|---|---|
| `MIN_FILES=15000` | 元のファイル数が下限を割ったら **rsyncを一切走らせずに中止**（実測22,575件の約7割） |
| **空実行 → 件数を数える → 本番** | `MAX_DELETE=50` 件を超える削除が予定されていたら、**1件も触らずに中断**して通知を出す |
| `--max-delete=50` | 本番側にも同じ上限を付ける（空実行と本番の間に元が変わった場合の保険） |
| ロック（`mkdir .lock`） | 前回が終わっていなければ二重に走らせない（macOSに `flock` は無い） |
| `--itemize-changes` | 何を追加・更新・削除したかをログに残す。「いつ消えたか」を後から追える |

### なぜ空実行を先にやるのか

`--max-delete=50` だけだと **「50件消してから止まる」**（＝一部は消えてしまう）。
「消える前に止めて人が見る」ためには、先に `rsync -n` で `*deleting` 行を数えるしかない。
超えたときは削除予定の先頭200件をログに書き出すので、それを見て判断する。

正しい削除だと判断したら、上限を上げて手で流す:

```bash
MAX_DELETE=99999 bash /Users/apple/dropbox-backup/backup.sh
```

**中断した週はバックアップが古いまま止まる。** 社内の整理でフォルダを1つ移しただけでも
50件は簡単に超えるので、通知（`osascript display notification`）と `last-run.txt` で気づくこと。

## 調べて分かったこと（同じ調査を繰り返さないため）

### 1. macOS の `/usr/bin/rsync` は GNU rsync ではなく **openrsync**

`--backup --backup-dir=` で「消したファイルをゴミ箱フォルダへ退避する」つもりだったが、
**openrsync は `--backup` を付けると `--delete` が効かなくなる**（消えるはずのファイルが
先に残り続け、ミラーにならない）。2026-08-31 に実測して確認:

```
src: keep.txt          dst: keep.txt(古い) + gone.txt
rsync -a --delete --backup --backup-dir=trash src/ dst/
  → dst に gone.txt が残ったまま。trash に入ったのは上書きされた keep.txt だけ
```

`--delete-after` に変えても同じ。よって**退避フォルダ方式は使えない**ので、
素の `--delete` ＋ 安全弁 ＋ 削除ログという構成にした。
（`--backup-dir` `--max-delete` `--itemize-changes` `--stats` 自体はヘルプにあり受け付ける）

### 2. `--inplace` が無いと、名前の長いファイルで rsync ごと落ちる

openrsync は転送中に `.<元の名前>.XXXXXXXX` という一時ファイルを作る。元の名前が長いと
**この一時名が 255 バイトを超え、UTF-8 の途中で切られて** `mkstempat: Illegal byte sequence`
となり、そこで rsync が終了する（2026-08-31 の初回実行が 19,050 件目で落ちた）。

該当したのは共有フォルダ全体で **2件だけ**（最長 299 バイトの PDF。どちらも
`社内・総務/研修・資料/〔疑問点を紐解く〕インボイス制度Ｑ＆Ａ…`）。数え方:

```bash
LC_ALL=C find "<元>" -type f | awk -F/ '{n=length($NF); if(n>m){m=n}} END{print m}'
```

`--inplace` は一時ファイルを作らないので通る。**代償**は「転送が途中で切れると転送先が
半端な状態で残る」こと。ただし mtime が合わなくなるので次回の実行で必ず転送し直される。

### 3. launchd から Dropbox(CloudStorage) を読むには `/bin/bash` にフルディスクアクセス

plist は `/bin/bash backup.sh` を呼ぶ。**ここから直接コマンドを叩いてはいけない**
（TCCの責任プロセスが bash でなくなり、CloudStorage が読めなくなる）。
`shorui-cabinet` `jyuusetsu-research` `file-finder-inventory` と同じ事情。

### 4. オンライン専用（未ダウンロード）ファイルが1,315件・約0.8GB あった

`stat` の `st_blocks==0` かつサイズあり、で数えられる。rsync が読むと Dropbox が
実体を落としてくるので、**初回はローカル使用量が約0.8GB増える**。異常ではない。

### 5. 非UTF-8ロケールだと `"$VAR）"` が未定義変数になる

launchd はロケールを渡さない（`LANG` が空＝C ロケール）。この状態の bash は
**`$MAX_DELETE）` の全角括弧までを変数名として読む**ため、`MAX_DELETE）: unbound variable`
で `set -u` に落ちる。2026-08-31 に実際に踏んだ（ログが4行で止まり、原因が見えなかった）。

対策は2つ入れてある。**スクリプト先頭で `LANG`/`LC_ALL`/`PATH` を明示する**ことと、
**変数を必ず `${VAR}` と波括弧で書く**こと。日本語をログに出すスクリプト全般に効く話。

### 6. 日曜 5:00 の `file-finder-inventory` の後に走らせている

5:00 に `全ファイル一覧.xlsx` が作り直されるので、6:00 にすると出来たてを一緒に運べる。

## 保存先に残っている 2026-07-04 の手動コピーについて

`社内バックアップ/` 直下には、7月に手でコピーしたとみられる古い一式
（`営業・募集` `管理業務` `業者・設備管理` `経理・請求書` `社内・総務`
`管理物件台帳.xlsx` `フォルダ構成一覧.xlsx`）がある。
**このスクリプトは触らない**（`（★必読★）新共有フォルダ/` という別のサブフォルダへ入れる）。
直下をミラー先にすると `--delete` が上の古い一式を消してしまうため、意図的に分けた。
不要と判断したら手で消すこと。
