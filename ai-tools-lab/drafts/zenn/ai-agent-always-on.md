業務チャットに常駐して、会話からTODOを拾い、社内資料を検索して質問に答えるエージェントを
作りました。**手元で動かしていたときには一度も出なかった問題が、常駐させた途端に出ます。**

「作れるか」ではなく「**動かし続けられるか**」で詰まった4つを残しておきます。

## 1. 子プロセスが終了コード -11 で不定期に落ちる

AI呼び出しをCLIの子プロセスとして実行していたのですが、不定期に落ちました。

```
subprocess exited with code -11
```

**-11 は SIGSEGV**（セグメンテーション違反）です。Pythonのコードが悪いなら例外が出るはずで、
そもそも例外になっていないのが不気味でした。

**原因は、仮想環境（venv）のPythonから子プロセスを呼んでいたこと。**
同じコードをシステム標準の `/usr/bin/python3` から実行すると再現しません。

```diff
 <!-- 常駐サービスの定義 -->
-<string>/path/to/.venv/bin/python</string>
+<string>/usr/bin/python3</string>
```

再現条件を詰め切れていないので断言は避けますが、**別アプリでも同じ組み合わせで再現**しました。
CLIツールを子プロセスとして呼ぶ構成なら、まず実行系のPythonを疑ってください。
依存パッケージは `--target` で別ディレクトリに入れて `PYTHONPATH` を通せば、
venvを使わなくても管理できます。

## 2. 二重起動して、同じ返信を2回投稿する

常駐サービスが二重に立ち上がり、**同じ内容を2回投稿しました。** 相手のある機能なので、
これは実害が出ます。

起動スクリプトが多重起動を防いでいなかったのが原因です。「二重に起動しないよう気をつける」
は運用でカバーする話ではないので、**構造的に1つしか動けない形**にしました。

```python
import fcntl, sys

lock = open("/tmp/agent.lock", "w")
try:
    fcntl.flock(lock, fcntl.LOCK_EX | fcntl.LOCK_NB)
except BlockingIOError:
    sys.exit(0)   # 2個目は黙って終了する
```

ロックはプロセスが死ねばOSが解放するので、**強制終了しても残りません。**
PIDファイルを自前で消す方式より確実でした。

外部へ投稿する常駐は、**同時に1台だけ**という制約も併せて必要です。
開発機と本番機の両方で起動していると、二重投稿は簡単に起きます。

## 3. 日本語の全文検索で、本命の資料が上位に来ない

社内資料の検索に SQLite の FTS5 を使いました。動くには動くのですが、
**探している資料が上位に来ません。**

原因は2つありました。

- **分割方式**: 既定のトークナイザは空白で区切る前提で、日本語だと語の切れ目を拾えない
- **表記ゆれ**: 半角カナ・全角カナ・記号の違いで別語として扱われる

**直し方**: 3文字単位で索引する方式（trigram）に変え、登録時と検索時の両方で正規化を通す。

```python
import unicodedata
def norm(s: str) -> str:
    return unicodedata.normalize("NFKC", s).lower()
```

```sql
CREATE VIRTUAL TABLE docs USING fts5(body, tokenize = 'trigram');
```

あわせて、**検索の取得件数を8件から12件に増やしました。** 上位8件で切っていたせいで、
本命が「もう少し下」に埋もれていたためです。この2点で、**圏外だった資料が1位**に来ました。

ノイズの掃除も効きます。テンプレートや空ファイルを無効化して、
**有効文書 4,057件 → 3,838件**（219件を除外）。母数を減らす方が精度は上がりました。

## 4. 常駐にした途端、クラウドストレージ配下が読めなくなる

手元では読めていたフォルダが、常駐サービスから読めません（macOS）。
プライバシー保護（TCC）による制限です。

ここが本題で、**Python本体にフルディスクアクセスを与えても解決しません。**

TCCは「どのプロセスの責任か」で判定します。常駐サービスの定義が

```xml
<key>ProgramArguments</key>
<array>
  <string>/bin/bash</string>     <!-- ← 責任を持つのはこちら -->
  <string>/path/to/run.sh</string>
</array>
```

となっている場合、**責任プロセスは `/bin/bash` の側**です。つまり
`/bin/bash` にフルディスクアクセスを与える必要があります（GUIでの手作業が1回要ります）。

ターミナルから同じスクリプトを叩くと読めてしまうのも紛らわしい点です。
その場合の責任プロセスはターミナル側で、そちらは権限を持っているためです。
**「手で動かすと読めるのに、常駐だと読めない」はこの構図を疑ってください。**

なお権限が無い場合でも他の機能は動くよう、例外を握って画面に案内を出す形にしました。
**権限が1つ足りないだけで全機能が止まる**のは、常駐サービスとしては困ります。

## まとめ

4つとも、**単発実行では絶対に出ない**種類の問題でした。常駐させるというのは
「同じコードを、権限も生存期間も違う場所で動かす」ことなのだと実感しています。
