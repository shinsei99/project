## iPhone 対応で分かったこと（2026-08-17 実機実測・iOS 18.7 / Safari 26.5.2）

**iPhoneのブラウザは全部Safariの中身。** Chrome(CriOS/152) も `vendor: Apple Computer, Inc.` /
`AppleWebKit/605.1.15` で、機能はSafariと同一だった。→ **フォルダ指定（`showDirectoryPicker`）は
iPhoneでは使えない**（`false`。`showOpenFilePicker` も `false`）。使えるのは `<input type="file">` のみ。

| 項目 | iPhone の実測 | 設計への影響 |
|---|---|---|
| WebPの**書き出し** | **できない**（`toDataURL("image/webp")` がPNGで返る。1ページ583〜670KB） | **画像はMacで作って持ち込む。iPhoneでは生成しない** |
| WebPの表示 | 要確認（Safari 14+ は対応しているはず・未実測） | Macで作ったWebPを表示できる前提 |
| IndexedDB / serviceWorker / storage.persist | すべて使える | 索引の持ち込み・オフライン起動・データ保護は成立 |
| 1ページの描画＋圧縮 | 60〜110ms | 速度は問題にならない |
| 保存容量 | **プライベートブラウズだと保存が壊れる**（下記） | **検知して案内する必要がある** |

### ⚠️ プライベートブラウズでは保存できない（実機で踏んだ）

Safariのプライベートタブで IndexedDB に書こうとすると**エラー内容が `null` のまま失敗**し、
`navigator.storage.estimate()` の上限も 1000MB と小さく申告される（通常モードのChrome(CriOS)では
30MBが0.1秒で書けて上限38.4GBと申告）。**同じエンジンなのに挙動が違うのはブラウズモードのせい。**

→ アプリ側でやること: **保存を試す前に小さな書き込みで判定し、失敗したら
「プライベートブラウズでは保存できません。通常のタブで開いてください」と画面に出す**。
いまは無言で失敗するので、原因が分からない。

## いま着手していること（2026-08-17 夜・設計変更 v3）

**「軽い索引を持ち歩き、重い原本はDropboxに置く」形へ作り替える。** App Store 前提なので
Mac があることを前提にしない（Macのフォルダ一括指定は将来の「速い道」として残す）。

- [x] ① **保存できない状態の検知**（プライベートブラウズ等で無言に失敗する。起動時に1KB書いて判定）
- [x] ② **取り込みは索引だけ**（テキスト抽出のみ。1ページ1ms）。**ページ画像は見たときに作ってキャッシュ**
      （iPhoneはWebPが作れないのでJPEGへ自動フォールバック）
- [x] ③ **複数ファイルの一括取り込み**（1冊ずつ処理して重複は飛ばす。中断しても既に入った本は残る）
- [x] ④ **書き出し／読み込み**（索引のみ・JSON。画像キャッシュは入れない＝見れば作り直せる）
- [x] ⑤ **本棚（表紙を並べる）＋読書画面**。表紙は取り込み時に1枚だけ作る（1冊30〜60KB）。
      読書画面は明朝/ゴシック・文字サイズ・行間の調整、しおり、前後ページ、紙面への切替
- [x] ⑥ **本文の組み直し**（縦書きの列復元・柱とノンブルの除去・段落の連結）と**品質の表示**（バックアップ＝端末故障対策と、端末間の受け渡しを兼ねる）

### なぜこの形か（実測に基づく）
- テキスト抽出は**1ページ1ms**、ページ画像化は**60〜110ms**。重いのは画像化のほうなので、
  **全ページ画像化をやめる**だけで取り込みが桁で軽くなる
- 全ページ画像を持つと3万ページで4.2〜6GB。**見たページだけなら数十MB**
- 原本は Dropbox に置いたまま。**索引作成中に必要な空き容量は「1冊分（最大320MB）」だけ**
- 一度読んだ実体は Dropbox が保持し続ける（実測: 3冊読んだら 0B → 452MB）。**解放は明示的に**

## OCR補正の検討結果（2026-08-17 実測）

**ルールベースの補正だけでは足りない。** 実データで測った効果:

| 手段 | 効果（実測） | 判断 |
|---|---|---|
| 座標から組み直す（実装済み） | 崩れたページが**3/25 → 22/25 読める形**に | **採用** |
| 柱・ノンブル除去＋段落連結（実装済み） | 「55企業レベルの戦略策定魔されない…」→ 見出しと本文に分離。「泊2食付」→「1泊2食付」 | **採用** |
| 文字の正規化＋同形異字の寄せ（NFKC・力→カ・工→エ 等） | ひらがな率 19.8% → **21.1%**、ゴミ行 7,861 → 6,705 | 効果は小さいが副作用も小さい。**未実装** |
| ブラウザ内で再OCR（tesseract.js） | 未検証。日本語縦書きは苦手・1ページ数秒・言語データ20MB超 | **保留**（ページ単位のオプトインなら可） |
| LLMで文脈補正 | 精度は最も高い見込みだが**外部送信が必須**（完全オンデバイス方針と衝突）＋費用 | **既定オフの任意機能としてのみ検討** |

**直せない例**: 「邪魔されない」→「魔されない」のような欠落は、規則では復元できない。
図解ページの誤認（`ｎ工シ万弐`）も同様。→ **そこは紙面を見るのが正解**なので、
ページ単位で崩れを検知して「紙面を見る」を出す形にした（実装済み）。
