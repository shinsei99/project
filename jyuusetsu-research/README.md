# AI重説アシスタント（旧: AI重説調査 〜 Excel自動入力システム）

不動産業務の「物件調査 → 登記簿解析 → 重説下調べ → **全宅連の公式書式へ自動入力**」を
一気通貫で行う**調査支援・下書き生成**システム（Streamlit・port 8536）。
最終ゴールは宅建士が確認できる「重要事項説明書・契約書のドラフト（Excel）」の自動生成。
完全自動ではありません（**取引条件＝賃料・売買代金・引渡日は人が打つ**）。

## 設計方針

- すべての情報は `models/property_data.py` の **PropertyData**（単一辞書）に集約。
- **入力 → 調査 → 整理 → 出力（Excel / PDF）** の一方向パイプライン。
- AI文章はテンプレート生成（OpenAI 等の有料LLMは不使用）。
- Google Maps は**座標の精度が上がるときだけ**使う（下の「ジオコーディングの選び方」）。
  キーが無いPCでは従来どおり国土地理院だけで動く。
- API失敗時もアプリは停止せず、空欄（「要確認」）で継続。

## 入力

1. 住所（必須）
2. 登記事項証明書（土地PDF）
3. 登記事項証明書（建物PDF）
4. 物件概要書PDF（任意・将来対応）

## 調べて分かったこと（次の担当が同じ調査を繰り返さないため）

### ★紙面を見ないと分からない事故が6件あった（2026-08-27）

**「どの項目がどのセルに入ったか」を突き合わせても、書面が壊れていることは分からない。**
2026-08-27 に初めて印刷イメージを1ページずつ見たところ、値の対応表は全部埋まっているのに
**紙の上では6箇所が壊れていた**。以後、書式まわりを触ったら `print_check.py` を回して
**紙を見る**こと。

| 症状（紙の上） | 原因 | 対処 |
|---|---|---|
| チェック欄の□が所有者名・床面積に置き換わっていた | 公式書式は□のセルにも色を付け数式で参照するので、入力欄として拾われる | `_is_checkbox()`＝**中身が□のセルには書かない** |
| 見出し「敷地権の種類」の上に地積が印字 | 見出しのセルにも色が付いている | `_has_text()`＝**すでに文字があるセルには書かない**（200本中4件が該当） |
| 所在・登記所在・地積が1列ずつずれた | 売買の書式に住居表示欄が無く、列見出しが「登記簿面積」 | 登記所在を先に決める／**住居表示の欄が無い書式には書かない**／地積の予備見出しに「登記簿面積」 |
| 区分所有で**一棟**の構造・延床面積に専有部分の値 | 見出しがどちらも「構　造」「床面積」 | `_section_for()`＝**まとまりの見出し**（帳票いちばん左の縦見出し）を除外判定に使う |
| 建物の「所在」が空 | 1項目＝1セルの対応表 | `resolve(..., extra=)` が**別のまとまりの2箇所目**を返す（土地・建物・物件のときだけ） |
| 床面積が「新築：」の年月欄へ／延床面積しか無い書式で空 | 「延床面積」も「床面積」を含む | 素の床面積を先に（`(?<!延)`）、無ければ「計」「（登記簿）」「延床面積」 |

**所有者は書式へ自動入力しない。** 公式書式に氏名欄が無く、あるのは
「登記名義人と □同じ ／ □異なる→理由」というチェックだけ。ここへ名前を書くと意味が変わる。

### 印刷イメージの作り方 — **LibreOffice は要らない**（2026-08-27）

過去の記録に「Excel の AppleScript PDF 化は -50 で不可」とあるが、**構文違い**だった。

```applescript
tell application "Microsoft Excel"
  set wb to open workbook workbook file name POSIX file "/path/to.xlsx"
  save wb in POSIX file "/path/to.pdf" as PDF file format
  close wb saving no
end tell
```

これで**ブック全体（76ページ）**が1本のPDFになる。画像化は poppler の `pdftoppm -png -r 110`。
`qlmanage` は1ページ目しか描けないので使わない。道具は `print_check.py` にまとめてある。

- **Excel のウィンドウが開く**（作業中の Excel があるときは注意）。開いたブックは保存せずに閉じる
- 出力は `reports/print_check/`（gitignore）

### 管理費・修繕積立金の欄は「入力欄」ではない（2026-08-27）

区分所有の重説でいちばん効く

    通常の管理費（月額・滞納額）／計画修繕積立金（月額・滞納額・積立総額）

は、**全宅連の書式では色も数式参照も付いていない**。したがって色と参照から入力欄を割り出す
`field_map` からは**見えない**（画面には出るが書面に入らない、という状態だった）。

作りは規則正しく `見出し ｜ 記入枠 ｜ 円` なので、**単位「円」を目印にその1つ左の結合セル**を
取れば版が変わっても追随できる。これを `services/intake_fill.py` に分けた。
一棟の見出しが3行分の結合セルで**単位が次の行に回る**ことがあるので、数行下まで見ている。

### 旧Word（.doc）を表を壊さずに .docx へ変換する（`doc2docx.py`・2026-08-21）

全宅連の公式書式のうち14本が `.doc`（Word 97形式）で、python-docx が読めない。
一通り試した結果は次のとおり。**近道はなく、2段構えが要る。**

| 手段 | 結果 |
|---|---|
| Word の AppleScript `save as` | **使えない**。3通りの書き方すべて `-1708 メッセージを認識できません` |
| `textutil -convert docx` | **表が壊れる**。docx書き出し側の問題（.docx→.doc→.docx で表15個→0個を実測） |
| `textutil -convert rtf` | **表は残る** |
| `pandoc -f rtf -t docx` | **表が残る**（要 `brew install pandoc`） |

→ **textutil で RTF にして pandoc で docx にする。**

**文字化けの落とし穴**: textutil が出す RTF は `\ansicpg932` を名乗り、一部の文字を
`\'xx` の生バイトで埋め込む。pandoc は cp932 を解釈できず（`Unsupported code page 932`）、
そこだけラテン文字に化ける（実測: 「年月日」→ `”NŒŽ“ú`、「亜細亜印刷」→ `ˆŸ×ˆŸˆóü`）。
本文の大半は既に `\uNNNN` エスケープなので、**残った `\'xx` の連なりだけ CP932 として
解釈し直して `\uNNNN` に書き換える**。承諾書では該当は16バイトだけだった。これで化けは0になる。

**変換結果（14本）**: 文字化け0。うち**6本は表を持つ**（承諾書・通知・説明書）ので
流し込みの対象になる。残り8本は規則・モデル条項で、もともと入力表が無い文章もの。
`textutil` だけで見たときに「14本すべて表0」に見えたのは**変換器が壊していただけ**だった。


### ④ クロスチェック（`legal-crosscheck` を吸収・2026-08-21）

出来上がった重説・売買契約書を、**このアプリが調べた結果と謄本に突き合わせて検閲する**。
独立アプリ `legal-crosscheck` を取り込んだもので、元アプリは削除した。

**4者間の照合**: 🌐行政の正解（PropertyData）／📄謄本ファクト（PropertyData）／
📝重説（PDF抽出）／🛒契約書（PDF抽出）

| レイヤー | 内容 |
|---|---|
| ① 入力齟齬 | 地番・家屋番号・地積・床面積の一致、所有権登記名義人 vs 売主、契約日 vs 説明日 |
| ② 宅建業法 | 契約不適合責任の通知期間（40条・2年未満の制限）、違約金の20%制限（38条）、反社条項、手付倍返し |
| ③ 建築基準法 | 用途地域・建ぺい率・容積率の行政データ突合、セットバックの敷地算入の検算 |

#### 持ち込まなかったもの（意図的）

- **`admin_research_service.py`（モック）** … キー未設定のとき「新宿→商業地域80/600」のような
  **架空の値を"行政の正解"として返す**もの。その値を基準に赤字判定すると事故になる。
  行政データは `zoning_service`（XKT002・100m上限）が本物を取るので不要
- `registry_parser.py` / `geo_service.py` … `registry_service` / `address_service` に置き換え済み
  （後者は Google 併用で精度が上がっている）

#### 取り込む過程で直した元コードのバグ

1. **偽の「一致」**: 所有者名義 vs 売主が、謄本に所有者名があるだけで🟢一致を返していた。
   重説・契約書の売主欄が両方空でも緑になる（何とも照合していないのに一致と言う）。
   検閲ツールで偽の緑は見落としを生むので、相手側の値がある場合だけ一致にした
2. **必ず落ちる正規表現**: `document_parser._num_near` が `建ぺい率|建蔽率` のような選択を
   素で連結しており、前者に当たると `group(1)` が None になって例外。
   **建ぺい率の記載がある重説なら必ずクラッシュしていた**。非キャプチャ群で囲んで解決
3. **`--tools` の渡し方**（`web_law_service`）: 可変長引数なのに `"WebSearch WebFetch"` を
   1つの文字列で渡していた。ツールが解決されず **300秒でタイムアウト**していた。
   別々の引数にしたら **71秒で完了**するようになった

#### Web法令調査の実力（2026-08-21 実測）

防火地域・高度地区・日影規制は不動産情報ライブラリに無いので、`web_law_service` が
claude CLI の WebSearch で自治体の都市計画情報を見にいく。ただし**万能ではない**。

大阪市都島区の実測では、日影規制（規制なし）と地区計画の手がかりは返したが、
**建ぺい率・容積率・防火地域・高度地区は「確定できなかった」と空欄で返した**。
理由は「マップナビおおさかは地図GISの操作が必要で、WebSearch/WebFetch では届かない」。
**憶測で埋めずに空欄を返すのが正しい挙動**なので、これは仕様どおり。
確定値が要るときは自治体窓口に照会する。


### 公式書式への流し込みエンジン（2026-08-21 実装）

全宅連の公式書式186本（xlsx 74 / docx 112）に対し、**セル座標を人が書かずに**
`PropertyData` を流し込む。要は「見出しの文言から入力欄を割り出す」方式。

| 経路 | 対象 | 実装 |
|---|---|---|
| Excel | xlsx 74本（重説・売買契約書・自動入力書式） | `services/official_format_service.py` |
| Word | docx 112本（賃貸借契約書36・媒介契約書10ほか） | `services/docx_format_service.py` |
| 対応表 | 見出し→項目の規則（包含＋除外） | `services/field_map.py` |
| レジストリ | 走査結果のキャッシュ | `scan_formats.py` → `data/format_registry.json` |

#### 肝: excel版自動入力書式は「重説シートだけ埋めればよい」

1ファイルに重説・売買契約書・実測清算確認書・引渡し書・媒介手数料承諾書が同梱され、
**契約書側のセルが重説シートを参照する数式**になっている（同梱の注意事項シートに明記）。
実測で、他書式から参照されている重説セルは **90種類**。ここだけ埋めれば5書類が完成する。

入力欄は色で区別されている:
`FFFFFF99`(黄)=共通入力欄（他書式へ波及） / `FFCCFFCC`(緑)=選択欄 / `FFFFCC99`(橙)=その書式のみ。

#### つまずいた点（同じ穴を掘らないため）

- **見出しは左だけを見ても当たらない。** 左だけ→17項目中11、上の列見出しも見て15、
  **結合セルの左上を解決して17**。結合セルは左上以外の値が `None` になるため、
  「地　積」のような列見出しが拾えていなかった
- **除外規則が要る。** 「所在」は宅建業者の**主たる事務所所在地**にも出る。除外しないと
  業者の住所を物件所在地に書く。同様に「種類」に権利の種類、「地積」に地積の確定、
  「建蔽率」に緩和の欄がある
- **最寄駅・駅距離・人口・世帯数・路線価・公示地価は重説に記載欄が無い。**
  あれは調査資料であって重要事項説明書の記載事項ではない。画面に出すだけにする
- **書き込みは `xlsx_patcher`（無損失）を使う。** openpyxl で再保存すると図形・罫線が落ちる。
  検証で zipエントリ36→36・転記数式81本が健在であることを確認済み
- **Word は run を全部消して書き直すと書式が飛ぶ。** 先頭 run だけ差し替える。
  `(住居表示)` のような案内文は消さずに後ろへ足す
- **`.doc`（旧Word・14本）は python-docx で読めない。** Word で `.docx` 保存し直しが要る

### 自動入力を増やすために調べたこと（2026-08-23）

**書式に何個欄があって、いくつ埋まっているか**を数えるところから始めた。

| 書式 | 入力欄の総数 | 実測日 |
|---|---|---|
| 重説（土地建物の売買・交換用） | **647** | 2026-08-23 |
| 重説（区分所有建物の売買・交換用） | **663** | 同上 |

647のうち **64個は「都市計画法・建築基準法以外の法令に基づく制限」のチェック**
（古都保存法〜重要土地等調査法）。宅建士が1つずつ見ている欄で、ここが自動化の本丸。

#### 1枚目の宅建業者・宅建士欄は「1回登録すれば毎回入る」（`agent_fields`）

主たる事務所所在地 / TEL / 商号 / 代表者 / 免許証番号（知事名・更新回数・番号の3分割）/
宅建士の氏名 / 登録番号（都道府県・番号の2分割）/ 事務所名 / 事務所所在地 の
**12箇所**（実測）。物件ごとに変わらないのに毎回手打ちだった。

- コードは直下の共有モジュール **`company_profile.py`**。**値はコードに書かない**
  （このリポジトリは public）。実データは `config/company_profile.json`（gitignore）に置き、
  **別PCへは Dropbox で運ぶ**（`secrets-manifest.txt` に登録済み＝`./secrets-sync.sh` が拾う）
- **座標は書式ごとに違う**（200本ある）ので持たない。**行の中で「見出し → その右の入力欄」を対にする**。
  行の左端だけを見る作りだと、宅建業者売主版の「免許証番号 …｜宅地建物取引士 登録番号 …」のように
  **1行に見出しが2つ以上並ぶ型**を取りこぼす（実際に取りこぼしていた）
- 括弧で割れている欄（`（ ）第 号`）は、**その行で直前に出た見出し**が免許証番号なのか
  登録番号なのかで意味が決まる。出てきた順に当てる（免許は本体から、登録は括弧の中から始まる）

**値は過去に交付した実物の重説から取った**（2022年の事業用賃貸借・K1ビル）。
同じ書式の白紙に流し込み、**12欄すべてが一字一句一致する**ことを確認済み。

### 災害3項目の実装と、書式のチェック欄（2026-08-23）

`hazard_service` は **常に空文字を返すスタブ**だった（重説の災害欄が全部「要確認」に
なっていた）。不動産情報ライブラリの災害レイヤで実装した。

| 項目 | レイヤ | 元データ | 使うズーム（実測） |
|---|---|---|---|
| 洪水浸水想定 | XKT026 | 国土数値情報 A31a（**想定最大規模**） | 14（対応は14〜15のみ） |
| 津波 | XKT028 | 国土数値情報 A40（津波浸水想定） | 14（同上） |
| 土砂災害 | XKT029 | 国土数値情報 A33（土砂災害警戒区域） | 13（対応は11〜15） |

**レイヤ番号は総当たりで見つけた**（XKT001〜XKT035 を叩いて `_index` を見る）。
公式の一覧は当たりづらいが、`_index` に `bs030_flood_area_maximum_scale_…`
`bs031_sediment_disaster_alert_area_…` `bs032_tsunami_area_…` と実データ名が入っている。
ついでに分かったもの: **XKT014=防火地域** / XKT027=高潮浸水想定 / XKT025=液状化(地形分類)。

**コード値は公式コードリストで確認した（推測していない）**。

- 浸水深ランク `A31a_205`: 1=0〜0.5m / 2=0.5〜3.0m / 3=3.0〜5.0m / 4=5.0〜10.0m /
  5=10.0〜20.0m / 6=20.0m以上（`codelist/water_depth_code.html`）
- 現象種別 `A33_001`: 1=急傾斜地の崩壊 / 2=土石流 / 3=地滑り（`CodeOfPhenomenon`）
- 区域区分 `A33_002`: 1=警戒区域 / 2=特別警戒区域（`CodeOfZone_h27`）
- 津波の `A40_003` は最初から `"1.0～2.0m"` の文字列

**ズームは「使えるいちばん粗いもの」を選ぶ。** 同じ地点でも高ズームだと地物が
間引かれることがある（XKT014 は z14 で1件・z15 で0件になった）。
洪水・津波は z14〜15 しか受け付けず、範囲外は HTTP 400 で
「不正なズーム値（z）が指定されたため、検索できませんでした。」が返る。

**「区域外」と「判定不可」を分ける。** タイルに地物があって地点が外なら「区域外」と
言い切ってよいが、地物が1件も無いときは**データ未整備かもしれない**ので空欄
（＝要確認）にする。「確認できなかった」を「該当なし」と書くと重説の事故になる。

#### ★ 出典側の利用制限（兵庫県は重説の根拠に使えない）

国土数値情報 A33 の配布ページに都道府県ごとの但し書きがあり、
**兵庫県は「本データを宅地建物取引業法に基づく重要事項の説明等の根拠と
しないで下さい」と明記している**（岡山県＝境界確認の根拠不可、京都府＝商用利用不可）。
当社の営業エリアが該当するので、**取得できても下調べ止まり**。画面に必ず注意を出す
（`hazard_service.PREF_NOTICE` → `app.render_hazard_notes`）。

#### 書式の災害欄は「テキスト欄」ではなく「□」だった

`field_map` は災害3項目を書式のセルへ割り当てていたが、割り当て先は
**中身が `□` のチェックボックス**で、しかも3項目とも**「外」側の□**だった
（公式書式25本すべてで実測）。`hazard_service` がスタブの間は「空文字は書かない」
規則に救われていただけで、値が入った瞬間に**「外」の□が説明文に置き換わる**ところだった。

→ 災害3項目は `field_map` から外し、`checkbox_fill` が**土砂災害の「内」だけ**に
■を入れる（2026-08-23 オーナー判断）。「外」は人が押す。

- **津波は自動化しない**。取れるのは**津波浸水想定**（津波防災地域づくり法8条）で、
  書式が問うている**津波災害警戒区域**（同53条・知事指定）は**別の制度**。
  不動産情報ライブラリに警戒区域のレイヤは無い（XKT001〜035 を実測）
- **水害ハザードマップ欄も自動化しない**。あの□は「該当する図面における当該宅地建物の
  所在（＝地図を添付して示す）」のチェックで、浸水想定区域の内外を書く欄ではない

### 抵当権は土地と建物で分ける（2026-08-23）

重説の「登記記録に記録された事項」は**土地と建物で行が分かれている**のに、
`PropertyData` は `抵当権` を1つしか持たず、書式のマッピングは
**「抵当権」の字に最初に当たったセル＝建物側の詳細欄**を指していた。
そのため**土地の謄本しか無くても建物の欄に入る**（2026-08-21 に発見、この日まで未修正）。

- 共有パーサ `registry_parser.py` のスキーマに **`土地.抵当権` / `建物.抵当権`** を足した
  （トップレベルの `抵当権` は残す。**8517 が読んでいる**ため）
- `PropertyData` に `土地抵当権` / `建物抵当権` を追加
- `checkbox_fill.detect_rights()` が権利部(乙区)の **□抵当権 / □根抵当権** と
  その行の詳細欄を、土地ブロック・建物ブロックそれぞれで見つける
- **抵当権と根抵当権は別の権利**なので、文字列を見て分けて■を入れる
- **土地専用の重説には「土　地」「建　物」の目印が無い**（1つしかないので書く必要が
  ないため）。その場合はシート名（「土地の売買・交換用」等）から側を決める
- **どちらの不動産のものか分からないときは、どちらの欄にも書かない**。
  画面には「抵当権（土地・建物の別が不明）」として出し、人に判断させる

### ストリートビュー（未了・要 Console 設定）

`GOOGLE_MAPS_WEB_KEY` は **HTTPリファラが `https://daikyocorp.co.jp/*` に限定**されているため、
社内画面（`http://127.0.0.1:8599` 等）から Embed を開くと **403** になる（2026-08-20 実測。
撮影メタデータはサーバー用キーで取れるので「撮影時期 2021-08」は表示できている）。

**2026-08-21 に作成・設定済み。** キー名 `maps-embed-internal`（Maps Embed API 1個のみに制限、
アプリケーションの制限なし）。直下 `.env.google-maps` の `GOOGLE_MAPS_EMBED_KEY` に入れてある。
実測で埋め込みURLが HTTP 200、画面に「撮影時期 2024-09」が出ることを確認した。
**アプリケーションの制限を付けなかった理由**: 社内画面はポートが変わるのでリファラ制限だと
再び403になる。Maps Embed API は無制限・無料なので、制限なしでも課金は発生しない。

以下は作成手順の控え（同じキーを作り直すとき用）:

1. Google Cloud Console（プロジェクト `daikyo-maps-2026`）→ 認証情報 → **APIキーを作成**
2. 名前は `maps-embed-internal` など
3. **「APIの制限」で `Maps Embed API` **だけ**を選ぶ**（ここが肝。Embed は無制限・無料なので、
   このキーは**どう使われても課金が発生しない**）
4. 「アプリケーションの制限」はリファラでも「なし」でもよい。社内画面はポートが変わるので、
   リファラにするなら `http://localhost:*/*` `http://127.0.0.1:*/*` `http://192.168.1.105:*/*` を許可
5. できたキーを直下 `.env.google-maps` に **`GOOGLE_MAPS_EMBED_KEY=...`** として追記する

コード側は対応済み（`google_maps_api.embed_key()` が `GOOGLE_MAPS_EMBED_KEY` →
無ければ `GOOGLE_MAPS_WEB_KEY` の順で使う）。**キーを1行足すだけで表示される。**
- **規約**: ストリートビューは**印刷物に一切使えない**（チラシ・DM・重説の紙面は不可）。
  Google以外の地図と同一画面に並べない（この画面はハザードマップを"リンク"で置くだけ）

### 区分所有は「本体」と「車庫」で謄本が分かれる（2026-08-24 実測）

マンションでは**専有部分の謄本が本体（居宅）と車庫で別々に発行される**。
実例: OAPレジデンスタワー307号 …
本体 家屋番号 `天満橋一丁目1番20の1の307`（居宅・3階部分・72.59㎡・敷地権 1000万分の15863）／
車庫 家屋番号 `…の61`（車庫・地下1階部分・16.38㎡・建物の名称「車庫３４１－３４２」）。

- **謄本アップロードは土地・建物とも複数枚を受け取る**（共有パーサの上限は5枚）
- 共有パーサ `registry_parser.parse_registry` は複数枚を `_deep_merge`（後勝ち）で
  1件にまとめる。**素直に流すと後から読んだ車庫が本体の専有面積・家屋番号を上書きする**
  （＝渡す順で結果が変わる。再現しにくい事故）。2026-08-24 に
  **附属（車庫等）を先に、主たる建物を後にマージする**よう直した。
  主たる建物は従来キー `建物` / `マンション` に残り、附属は `建物一覧` / `附属建物一覧` に入る
- 本体か車庫かの判定は **①種類（「車庫」）→ ②建物の名称 →③室番号** の順。
  マンション型のJSONには「種類」の置き場が無く、`マンション.名称` は本体・車庫とも
  同じ一棟の建物名（「ＯＡＰレジデンスタワー」）になるので、**名称だけでは見分けられない**
- 画面では附属を主たる建物と**別の行**に出す（混ぜると車庫の面積が専有面積として書面に入る）

**実測（車庫を先に渡した場合）**: 専有面積 72.59㎡（本体のまま）／附属＝車庫341-342・16.38㎡。
修正前は 16.38㎡ が本体の専有面積として入っていた。

#### 会社の書き方（`重説-ＯＡＰ307号.xlsx`・2015年の実案件から）

| 欄 | 書き方 |
|---|---|
| 家屋番号 | `①天満橋一丁目１番20の1の307　②天満橋一丁目１番20の1の18` と**連記**（※`の18` は謄本の `の61` と食い違う＝当時の誤記と思われる） |
| 建物の番号 | `①307号　②車庫61号` |
| 種類 | `①☑居宅・□店舗・□事務所・②☑車庫`（**両方にチェック**） |
| 床面積 | **本体のみ**（壁芯 75.48 ／ 登記記録 72.59 ㎡）。車庫の 16.38 ㎡ は書いていない。付属建物欄は `☑無` |
| 車庫の敷地権割合・サイズ | 下の備考行に文章で（`分譲車庫 61号の敷地権の割合…1000分の824`） |

**2026-08-24 にオーナー確認済み。この書き方を既定にした。** 実装は次のとおり:

- 連記した文字列は `家屋番号記載` / `種類記載` という**別のキー**に入れ、`field_map` は
  そちらを書式へ流す。素の `家屋番号` / `種類` は**本体の値のまま**残す
  （`law_validator` のクロスチェックは契約書側と1対1で突き合わせるため、
  連記した文字列を入れると不一致だらけになる）
- **床面積は連記しない**（本体のみ）
- 車庫の敷地権割合・サイズは**自動で書き込まない**。「備考」は書式内に複数あって
  機械で当てると誤爆するので、画面に出すだけにして人が転記する
- 附属の「種類」が空のときだけ、建物の名称の頭（「車庫３４１－３４２」）から
  `車庫` `駐車場` などを補う。それ以外は**推測しない**

### 正規表現フォールバックは罫線を拾っていた（2026-08-24 修正）

謄本は罫線アート（`┏━━┯┃`）の表なので、`[^\n]+` で拾うと隣のセルや見出し行まで
まとめて取れる。実測では車庫の謄本で AI 解析が `JSONDecodeError` になり、フォールバックの
正規表現が **種類に `│ ② 構 造 │ ③ 床 面 積 ㎡ │ 原因及びその日付…` を入れて**いた。
さらにそれが本体側の値を上書きしていた。

- 拾った値は `_cell()` で**最初のセルだけ**にし、見出し語（種類・構造・床面積・原因及び…）なら捨てる
- `re.search` は見出し行に先に当たるので、`re.finditer` で**最初の中身のある値**を採る

> **2026-08-23 追記**: ここに書いてある `format_export_service.FORMATS` の仕組みは
