社内の書類を索引にして質問に答えるAIエージェントを運用しています。
契約書・報告書・業務マニュアルを全文検索し、根拠つきで答える、いわゆる社内RAGです。

ここに要件が来ました。

> **すでに退職した担当者の名前を、回答に出さないでほしい。**

資料には当時の担当者名がそのまま書かれています。だから「この物件の担当は誰？」と聞くと、
退職者の名前が、あたかも現在の担当のように返ってきます。

やることは単純に見えます。旧担当 → 現担当の対応表を作って置き換えるだけです。
**この「だけ」で2日はまりました。** 日本語の固有名詞は、そんなに素直に切り出せません。

## 前提：書類そのものは書き換えない

先に方針だけ。**原本は直しません。**
「当時の担当が誰だったか」は過去の事実として正しい記録なので、資料としては残します。
直すのは **回答するときの見え方だけ** です。

対応表は設定値として持ち、管理画面から増減できるようにしました。

```python
def staff_alias() -> list:
    """資料に残る旧担当者 → 現在の担当。[(旧, 新), ...] を返す。"""
    raw = get_setting("staff_alias", "") or ""   # 「旧→新」のカンマ区切り
    out = []
    for part in raw.replace("，", ",").split(","):
        part = part.strip()
        for arrow in ("→", "->", "=>"):
            if arrow in part:
                old, new = (s.strip() for s in part.split(arrow, 1))
                if old and new:
                    out.append((old, new))
                break
    return out
```

## 失敗1：プロンプトに書いても漏れる

最初はプロンプトだけで済ませようとしました。

```
★次の人は退職済み。名前を一切出さないこと: ◯◯さん・△△さん
資料にこの名前が出てきたら、現在の担当に置き換えて書く
```

守られる確率は上がります。**上がるだけです。**
長い回答、引用の多い回答、複数の資料をまとめた回答では、普通にすり抜けます。

生成側への指示は「お願い」であって保証ではありません。
**出してはいけないものは、出口で機械的に落とす。** 回答文字列の最終段に関門を置きました。

```python
text = generate_answer(question)      # ここは確率的
text = redact_retired(text)           # ここは確定的
send(text)
```

プロンプトの指示は消していません。二重にしただけです。
（プロンプト側も直しました。ただしこのとき別のミスもしています。
本番で使われているのは別の関数で、直したほうはフォールバック専用でした。
「どの関数が本番か」を確かめずに直すと、丸一日ぶんの修正が1つも効きません。）

## 失敗2：素朴な置換が、建物の名前を書き換える

関門の中身を、最初はこう書きました。

```python
text = text.replace(old, new)   # ← これが事故
```

社内の資料に出てくる姓は、人だけを指していません。索引を実際に数えました。

| その姓の出方 | 件数 | 置換してよいか |
|---|---|---|
| 社員の呼び方（`◯◯さん`） | — | ✅ 置き換える |
| **建物の名前**（`◯◯ビル ××町`） | **24チャンク** | ❌ 建物であって人ではない |
| **別人のフルネーム**（オーナー・取引先） | **15チャンク** | ❌ 実在する別の人 |

素朴に置換すると `◯◯ビル` が `△△ビル` になります。
実在しない建物名が、社内問い合わせの回答として配信されるわけです。

これは日本語特有の面倒さです。英語なら `\b` で語境界を取れますが、
**日本語には語と語の区切りが無い**ので、`◯◯` が人名なのか建物名の一部なのかを、
文字列だけでは判断できません。

### 手がかりは敬称だった

実データを見ると、切り分けの手がかりは1つありました。**社員には敬称が付く。建物には付かない。**

```python
for old, new in alias:
    text = re.sub(rf"(?<![一-鿿]){re.escape(old)}(さん|氏|様|君|殿)", rf"{new}\1", text)
```

2つの条件を入れています。

- **後読み**：敬称（`さん` 等）が続くときだけ置換する → `◯◯ビル` は当たらない
- **先読みの否定** `(?<![一-鿿])`：直前が漢字なら当てない
  → `××◯◯さん` のようなフルネームの一部を、姓だけ差し替えてしまう事故を防ぐ
  （`一-鿿` は U+4E00–U+9FFF、CJK統合漢字の範囲）

置換後も敬称を残したいので、敬称はキャプチャして `\1` で戻します。

ここまでで、こう動きました。

- `立会い担当は◯◯さん` → 置換される（狙いどおり）
- `◯◯ビル ××町` → そのまま
- `ファミリーホーム（◯◯ビル）` → そのまま

## 失敗3：「様」を入れたせいで、社外の人が別人にすり替わった

翌日、実際の回答を見ていて気づきました。

```
◯◯ビル ××町のオーナーは △△様 です
```

**オーナーの名前が、社内の別の人の名前に化けていました。**

共有フォルダを調べて分かったのは、この会社の書き分けです。

> **社員には「さん」、社外には「様」。**

そして旧担当と同じ姓の**オーナーが実在**していました。
管理台帳にも連絡先一覧にも見積書にも、電話番号つきで載っている実在の人です。
敬称の一覧に `様` を入れたせいで、その人の名前を別人の名前に置き換えていました。

修正は1文字の削除みたいなものです。

```python
for old, new in alias:
    # 「◯◯さん」だけを対象にする。
    # フルネーム（××◯◯さん）・建物名（◯◯ビル）・社外の人（◯◯様）には当たらない
    text = re.sub(rf"(?<![一-鿿]){re.escape(old)}(さん)", rf"{new}\1", text)
```

判断の理由も残しました。

> **置き換え漏れ（古い名前が残る）より、実在する別人の名前に化けるほうが、はるかに害が大きい。
> 迷ったら当てない側に倒す。**

伏字・匿名化・置換の類は、たいてい「漏れ」を怖がって強く当てにいきます。
でも過剰置換の失敗は**事実の捏造**になります。回収コストが違います。

## 検索側も直さないと、片側だけ効いて何も出なくなる

表示だけ読み替えると、次はこうなります。

```
Q: 現担当の△△さんが担当している物件は？
A: 該当する資料が見つかりませんでした
```

当然です。資料には旧担当の名前しか書かれていないのに、検索語は新しい名前だからです。
検索語のほうを**両方向に**広げました。

```python
def _expand_terms(terms: list) -> list:
    """新しい名前で引いたら旧い名前も見に行く（逆も同じ）"""
    alias = staff_alias()
    extra = []
    for t in terms:
        for old, new in alias:
            if old in t and new not in terms:
                extra.append(new)
            elif new in t and old not in terms:
                extra.append(old)
    return terms + [e for e in dict.fromkeys(extra) if e not in terms]
```

**入口（検索語）は広げ、出口（表示）は絞る。** 向きが逆です。
片方だけ実装すると「名前は消えたが何も引けない」か「引けるが古い名前が出る」のどちらかになります。

## 生成物にも同じ関門が要った

社内向けの業務マニュアル（静的HTMLを生成するスクリプト）にも同じ問題がありました。
本文の該当箇所を直して終わり、にはなりません。
**このスクリプトは生成時にクラウド上のWord/Excelを読みます。**
原本に古い名前が残っている以上、作り直すたびに復活します。

そこで、出来上がったHTMLを書き出す直前にもう一度通しました。

```python
RETIRED = {"旧姓1": "現姓1", "旧姓2": "現姓2", ...}

def rename_retired(text):
    for old, new in RETIRED.items():
        text = re.sub(r"(?<![一-鿿])" + old + r"(?=さん)", new, text)
    return text

HTML = rename_retired(HTML)   # ★書き出す直前に必ず通す
with io.open(OUT, "w", encoding="utf-8") as f:
    f.write(HTML)
```

実測結果です。

- 本文の置き換えは **19か所**（対象4名の内訳は 3・15・1か所、1名は0件）
- 置き換えの**前後とも「旧姓＋様」は0件**
  → 社外の人の名前には一切触れていないことを、件数で確認できた

最後の1行が地味に大事です。
「当てた件数」だけを見ていると、**当ててはいけないところに当たっていないこと**を確認できません。
過剰置換を疑うなら、**当たらなかったはずの側を数える**必要があります。

## まとめ

1. **生成側への指示は保証ではない。** 出してはいけないものは、出口で確定的に落とす
2. **日本語には語境界が無い。** 同じ姓が人・建物・別人として並ぶ。文字列だけでは切り分けられない
3. **切り分けの手がかりは、書き手の習慣の中にある。** この現場では敬称が社内/社外の境界だった
4. **置換は漏れより誤爆のほうが高くつく。** 古い名前が残るのは不便、別人の名前に化けるのは捏造
5. **入口と出口で向きが逆になる。** 検索語は広げ、表示は絞る
6. **過剰に当てていないことは、当たらなかった側の件数で確認する**

「置換するだけ」に見える要件ほど、実データを数えてから書いたほうが早い、という話でした。
