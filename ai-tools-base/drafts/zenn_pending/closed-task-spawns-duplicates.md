業務チャットに常駐して、会話からTODOを起こし、進捗と完了を追いかけるエージェントを運用しています。

あるとき、担当者が物件を回って外観写真を送るたびに、
**物件1件につき1つ、新しいTODOが作られ続けている**ことに気づきました。
誰も新しい仕事を頼んでいないのに、やることリストだけが伸びていきます。

判定の精度の問題だと思って、プロンプトを読み直しました。違いました。
原因は **LLMに渡していた一覧から、1件が抜け落ちていたこと**でした。

## 仕組み — 重複を防ぐために、未完了の一覧を毎回渡す

会話を判定するとき、同じ部屋の未完了TODOを一覧にしてプロンプトへ埋め込んでいます。

```python
task_lines = "\n".join(
    f"  - task_id={t['id']} / {t['content']} / 担当={t['assignee_name'] or '?'} "
    f"/ 状態={t['status']} / 期限={t['due_date'] or '未確定'}"
    for t in open_tasks
)
```

```
# 既存の未完了TODO（重複を作らないため。更新・進捗・完了はこのidに紐付ける）
{task_lines}
```

LLMは各メッセージを `new_task` / `progress_update` / `completion` / `none` などに分類し、
既存TODOに関するものなら `target_task_id` を返します。ここまでは意図どおり動いていました。

## 保険の規則が入っていた

以前、別の不具合を直しています。
**事前にTODOが登録されていない業務の完了報告が、紐付け先が無いという理由で黙って捨てられていた**という問題です。
そこで規則を1つ足しました。

```
8. 分割した案件ごとの報告が、既存の未完了TODO（一覧参照）のどれにも該当しない場合は、
   target_task_id が見つからないからと黙って捨てない。new_task として登録し、
   task.report_status に実際の状態を入れること
```

捨てるより残すほうが安全だと考えました。この判断自体は、いまも間違っていないと思っています。

さらにその手前に、こういう規則もあります。

```
7. 1つのメッセージに、複数の独立した物件・案件についての業務報告がまとめて書かれることがある。
   このとき、まとめて1件のイベントにせず、案件ごとに別々のイベントへ分割すること。
```

**この2つが噛み合うと増幅器になります。** 1つの報告を物件の数だけ分割し、
分割したそれぞれが紐付け先を失い、その全部が新規TODOになる。

## 消えていたのは「まとめ役」の1件

担当者ごとに、`担当物件の巡回・確認作業` というまとめ役のTODOを1件だけ登録してありました。
個別の物件名ではなく、担当者単位の包括的なTODOです。
巡回報告はすべてこれに紐付くはずでした。

そのTODOが、**一部の物件の巡回完了報告を受けた時点で、全体の完了として処理されていました。**

そして一覧を作るSQLはこうです。

```python
OPEN_STATUSES = [STATUS_TODO, STATUS_DOING, STATUS_WAITING, STATUS_OVERDUE, STATUS_HOLD]

def open_tasks_in_room(room_id, include_ai_confirm=False):
    statuses = OPEN_STATUSES + [STATUS_AI_CONFIRM] if include_ai_confirm else OPEN_STATUSES
    ph = ",".join("?" * len(statuses))
    return query(
        f"SELECT * FROM tasks WHERE room_id=? AND status IN ({ph}) ORDER BY id",
        (room_id, *statuses),
    )
```

状態は全部で8種類あり、未完了とみなすのはこのうち5つ。完了は入っていません。
つまり **完了になった瞬間、そのTODOはLLMの視界から消えます。**

あとは自動でした。

1. まとめ役が一覧から消える
2. 巡回報告に紐付け先が無くなる
3. 規則7が報告を物件ごとに分割する
4. 規則8が、分割されたぶんをすべて新規TODOにする

**LLMは一度も間違った判断をしていません。** 渡された一覧の中で、規則どおりに動いていました。
壊れていたのは、一覧の作り方のほうです。

## 直し方 — 「起票しない」を規則として書く

紐付け先が消えても暴走しないように、**定例報告そのものを起票の対象外**にしました。

```
9. 写真（外観写真等）だけ、または写真＋一言（「〇〇を巡回しました」等）の、
   定例の巡回・現地確認の報告は、それ自体を new_task にしない。
   - 報告者の包括的な巡回TODOが未完了TODO一覧にあれば、報告された物件名が
     TODOの文言に完全一致しなくても target_task_id でそこへ紐付け、
     event_type="progress_update" とする（物件ごとに分割しない。ルール7より優先）
   - 該当する包括的な巡回TODOが見当たらない場合（最初から登録が無い、
     既に完了扱いになっている等）は、event_type="none" とし、new_task も作らない
   - ただし、巡回中に破損・違法駐輪・要修繕箇所など対応が必要な具体的な問題が
     見つかった場合は、その問題への対応自体を new_task にしてよい
```

あわせて、保険の規則7・8の側にも「これは適用外」と書き足しました。
**規則の優先順位は、優先される側だけでなく、される側にも書かないと効きません。**

変更はプロンプト15行の追記のみで、コード側の分岐は増やしていません。
実データのメッセージで新旧のプロンプトを流して、出力の差を確認しました。

- まとめ役のTODOが無い場合 … 修正前は新規TODO → 修正後は `event_type="none"`
- まとめ役のTODOがある場合 … `progress_update` でそこへ紐付け（物件ごとの分割は起きない）

## 同じ形を、前にも踏んでいた

一覧を作る関数のdocstringに、こう残っていました。

```python
"""同一ルームの未完了 TODO（analyzer の文脈・重複判定用）。

include_ai_confirm=True で status=AI確認待ち も含める（グローバルな OPEN_STATUSES
自体は変えない。ダッシュボード集計等、AI確認待ちを含めたくない既存呼び出しがあるため）。
呼び出し側にAI確認待ちのTODOが見えないと、それへの進捗報告を target_task_id で
紐付けられず、イベントが無言で捨てられる（実害確認済み）。
"""
```

**参照先が一覧から消えると、後段の判断が全部変わる。**
前回は「無言で捨てられる」方向へ、今回は「際限なく増える」方向へ出ただけで、原因の形は同じです。

## 教訓

- **LLMに渡す一覧は、入力ではなく世界の定義**。そこに無いものは、モデルにとって存在しない
- **フォールバックには適用範囲を書く。** 「該当が無ければ新規作成」は、
  該当が消えうる設計と組み合わせると増殖装置になる
- **状態の集合を絞るクエリは、LLMへの入力を絞るクエリでもある。**
  集計用の「未完了」の定義を、そのまま文脈生成に使い回さない
- **出力がおかしいときに、まずプロンプトを疑わない。** 何を渡していたかを先に見る

なお、規則を直しても**過去に誤って作られたTODOは残ります**。
自動で消すと正しい起票まで巻き込むので、そこは人が見て統合しています。
まとめ役のTODOが一部報告で完了に遷移する問題自体も未修正ですが、
再発しても新規TODOの量産にはつながらなくなりました。
