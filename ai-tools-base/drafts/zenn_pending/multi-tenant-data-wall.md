社内チャットに常駐しているAIエージェントに、**2つの会社の資料**を持たせています。

- 全社が入っているチャット … A社の場
- ある担当者との個人チャット … B社の場

索引（SQLite + FTS5）は1つです。放っておくと、**A社の場からB社の書類が検索できます。**
「絶対に混ぜないでほしい」という要件が出たときに何をしたか、その過程で踏んだ穴を残します。

## 方針: プロンプトで頼まない

最初に検討したのはシステムプロンプトでした。

> この場ではB社の資料に触れないでください。

これはやめました。理由は2つです。

1. **守られたかどうかを後から確かめられない。** 出力を全部読む以外に検証手段がない
2. **見えているものは、いつか出る。** 要約・引用・「関連しそうな資料」の提示など、経路がいくらでもある

**見えないものは漏らせない。** 索引の行ごとに会社を持たせ、検索の条件で落とす方向にしました。
プロンプトは取り違え防止の補助に留めます。

```sql
-- 自社の書類はその会社のものだけ。法令・判例・書籍は「共通」で両方から見える
AND d.company IN (?, '共通')
```

## 穴1: 検証そのものが誤っていた

壁を入れた直後、両方の入口から**同じ12件**が出ました。効いていないように見えます。

原因は2つありました。

**① 検証が誤っていた。** 検証スクリプトは入口の識別子（ルームID）だけを渡していたのに、
判定側は会社名の環境変数しか見ていませんでした。どちらも空扱いで既定の会社に落ちます。

**② 設計の穴でもあった。** 片方の値しか渡らない経路があるなら、そこで壁は緩みます。
検証の誤りとして片付けず、判定を1つの関数へ寄せました。

```python
def here() -> str:
    """いまどの会社の場から呼ばれているか。分からなければ既定の会社。"""
    c = (os.environ.get("CWAI_COMPANY") or "").strip()
    if c:
        return c
    rid = (os.environ.get("CWAI_ROOM_ID") or "").strip()
    m = _map()                       # 入口 → 会社 の対応表（設定から読む）
    return (m.get("rooms", {}) or {}).get(rid) or m.get("default") or ""
```

会社名 → 入口の対応 → 既定、の順に見ます。**どちらか片方しか渡らない呼び出しからでも決まる**のが要点です。

あわせて、対応表が読めなかったときは空文字を返し、**壁を外さない側に倒しました。**
空文字はSQL側で「条件を付けない」ではなく「そもそも判定不能」として扱います。

## 穴2: 検索の経路が2系統あった

対話から呼ばれる検索と、エージェントが道具として呼ぶ検索が、**別々のSQLを持っていました。**

先に直したのは対話側です。ところが道具側は自前のSQLを通るので効きません。
このとき、**他社の場から自社書類が10件見えていました**（実測）。

両方に同じ条件を入れ、ファイルの先頭に相互参照を書きました。

```python
def _company_sql():
    """★このモジュールは qa.py とは別のSQLを持っている。
       qa.py 側だけ直しても、道具はこちらを通るので効かない。同じ壁を両方に入れること。
    """
```

本来は共通関数に寄せるべきところですが、呼び出し側の事情が違い、
いまは「両方に書いて、書いてあることを明記する」で止めています。

## 穴3: 早期リターンが壁を素通りしていた

条件を組み立てる関数に、早期リターンが2か所ありました。

```python
def _kind_sql(kind_keys):
    if not kind_keys:
        return " AND (d.source_kind IS NULL OR d.source_kind='自社書類') ", []   # ← 素通り
    if "全部" in kind_keys:
        return " ", []                                                          # ← 素通り
    ...
    return f" AND ({own} d.source_kind IN ({marks})) " + cc, vals + list(cargs)  # ← ここだけ壁あり
```

末尾にだけ条件を足すと、上の2本を通った呼び出しには壁が付きません。
**分岐ごとに足すのではなく、先に作って全部の戻り値へ連結する**形に変えました。

```python
def _kind_sql(kind_keys):
    cc, cargs = _company_sql()          # ★先に作る
    if not kind_keys:
        return " AND (d.source_kind IS NULL OR d.source_kind='自社書類') " + cc, list(cargs)
    if "全部" in kind_keys:
        return " " + cc, list(cargs)
    ...
```

横断的な条件を後から足すときは、**戻り値の数を数える**のが確実でした。

## 穴4: 既定値つきのカラム追加で、取り込みが片側へ寄る

索引に会社の列を後から足すとき、既存データがあるので既定値を付けました。

```python
_ensure_column(conn, "knowledge_documents", "company",
               "TEXT NOT NULL DEFAULT 'A社'")
```

既存データにとっては正しい既定です。しかし**取り込み処理に会社を渡していなかった**ため、
B社のフォルダを取り込んでも `company = 'A社'` で入りました。索引の時点で壁を越えています。

`ingest_file` / `ingest_folder` に `company` を通し、CLI に `--company` を足し、
会社ごとの資料ルートを設定として持たせました。

**検索側の壁だけを見ていると、入口の壁が抜けます。** 読み出しと書き込みの両方を見る必要があります。

## 道具側は、黙って空を返さない

エージェントの道具（他ルームへの投稿、タスク作成、案件参照など）にもガードを入れました。
このとき、**拒否は理由つきで返す**ようにしています。

```python
def deny(room_id=None, what="この情報") -> dict:
    msg = f"別の会社のものなので、ここからは扱えません（いまの会社={here() or '不明'}"
    if room_id is not None:
        msg += f"／対象ルーム={room_id}"
    return {"ok": False, "error": msg + f"）。{what}は、その会社の入口で扱ってください。"}
```

空リストを返すと、エージェントは「該当なし」と解釈して**存在しないことにして先へ進みます。**
「無い」と「見せない」は別なので、そこは区別して返します。

## 検証: 語で数えると誤判定する

最後に、どう確かめたかです。

はじめは特定の語で検索して漏れを探しました。ある業許可の名前で引いたら、
A社側に1件当たります。漏れかと思いましたが、**その語はA社の申込書にも普通に出てくる言葉**でした。
語の有無は所属の証拠になりません。

やり方を変えて、**入口ごとに、見える書類を会社別に数えました。**

- 全社の入口 … 自社 4,378件 ＋ 共通 262件 ／ 他社 **0件**
- 個人の入口 … 自社 314件 ＋ 共通 262件 ／ 他社 **0件**

共通（法令・判例・書籍）が両方で同じ262件であることも、狙いどおりです。
**0であることを数で示せる形にしておく**と、次に索引を触ったときも同じ検証が回せます。

## まとめ

- 分離は**プロンプトではなくクエリと条件分岐**で作る。検証できる形にする
- 判定は**1関数に寄せ、複数の入力源をフォールバックの順で見る**。片方が欠けても決まるように
- 読み出し経路が複数あるなら**全部に同じ条件を入れ、相互に明記する**
- 横断的な条件は**早期リターンを数えて**、全部の戻り値に付いているか確かめる
- **既定値つきのカラム追加は、書き込み側の穴になる**。取り込みにも会社を通す
- 拒否は**理由つきで返す**。空を返すと「無い」と解釈される
- 検証は**語で探さず、件数で数える**
