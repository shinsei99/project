社内向けに作ったWebアプリが増えてくると、次に詰まるのは**不具合報告**でした。

届くのは「なんか動かない」「前はできたのに」だけ。報告フォームを置いても埋まりません。
かといって、報告する側が悪いわけでもない。**再現手順を書くのは、慣れた人にしかできない作業**です。

そこで**報告を書かせるのをやめて、AIに聞き出させる**受付を作りました。設計で効いた3点を書きます。

## 1. フォームではなく対話にする、ただし回数を切る

やっていることは単純で、要件を選ぶとAIが業務口調で質問を始めます。

- 症状が出るのはどの操作のときか
- いつからか
- 毎回起きるのか、たまにか

**最大4問**で打ち切ります。ここは意図的な制限です。

対話型は油断すると延々と聞き続けます。相手は本業の合間に答えているので、
**質問が5つを超えたあたりで離脱**します。聞き切れなくても、
「途中まで」で報告書になる方が、完璧を狙って0件になるよりずっといい。

**「ここまでの内容で送る」ボタンを常に出しておく**のも同じ理由です。
中断が異常系ではなく、正常系として扱われている状態にします。

## 2. 人が確実に知っていることは、AIに推測させない

最初は報告文からすべて（対象アプリ・不具合の種類・優先度）を推測させていました。
これが外れます。社内アプリは名前が似ているうえ、報告文には正式名称が出てきません。

**対象アプリと要件は、画面のプルダウンで選ばせる**方式に変えました。

```python
# 画面で選ばれた値は、AIの推測より優先する
kind = forced_kind or analysis.kind
app  = forced_app  or analysis.app
```

判断の分担はこうなります。

| 情報 | 誰が決めるか | 理由 |
|---|---|---|
| 対象アプリ | **人**（選択） | 報告者は確実に知っている。推測させる意味がない |
| 要件の種類 | **人**（選択） | 同上。4択なので選ぶ方が速い |
| 深刻度・優先度 | AI | 症状の説明から判断させる。人は自分の困りごとを過大にも過小にも言う |
| 件名・概要・原因推測 | AI | 文章化はAIの得意分野 |

**「AIに任せる/任せない」を機能単位ではなく、情報の項目単位で決める**と迷いません。
基準は「その情報を、目の前の人が確実に持っているか」です。

## 3. 出口は必ず人を通す

最後に起票して、報告書メールを作ります。ここで**送信まで自動化しませんでした。**

既定の動作は「メールアプリに**下書きを作って表示する**」。送信ボタンは人が押します。

```applescript
tell application "Mail"
    set newMessage to make new outgoing message with properties {subject:subj, content:body, visible:true}
    -- send は呼ばない。人が見てから押す
end tell
```

AIが作った文章が、確認されないまま人に届く経路を作らない。
**間違いが起きるかどうかではなく、間違いが起きたときに誰が気づけるか**で決めました。

起票先（GitHub Issues / Notion / Backlog / ローカルCSV）はアダプタで差し替えます。
導入初期はローカルCSVで動かして中身を確かめ、運用が固まってから外部サービスへ向けました。
**最初から本番の出口に繋がない**方が、検証中の事故が減ります。

## おまけ：macOSでメール下書きが最初の1回だけ失敗する

`osascript` で他アプリを操作するには、**オートメーションの許可**が要ります。
初回に許可ダイアログが出て、それを通すまで失敗します。

`launchd` から常駐させている場合は特に厄介で、
**ダイアログが出る画面が無いまま黙って失敗する**ことがあります。
一度ターミナルから手で叩いて許可を通しておくのが確実です。

権限が無いときは例外を握って画面に案内を出し、**他の機能は動かす**ようにしています。
権限1つで全機能が止まると、原因の切り分けができません。

## まとめ

- 報告が集まらないのは、報告者の怠慢ではなく**書式の要求が高すぎる**から。聞き出す側に回す
- 対話は**回数を切る**。途中終了を正常系として設計する
- **項目ごとに**「人が確実に知っているか」で、AIに任せるかを決める
- 出口（送信・公開）は人を通す。自動化しない場所を先に決めておく
