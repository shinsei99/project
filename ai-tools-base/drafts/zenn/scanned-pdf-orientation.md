登記簿（登記事項証明書）のPDFを読み取って、契約書のExcelに転記するツールを作りました。

読み取り精度が安定せず、プロンプトを何度も書き直したのですが、
**効いたのはプロンプトではなく、読ませる前に画像を回すことでした。**

## 症状

同じ種類の書類なのに、当たりと外れがある。

- 地番や床面積が空で返る
- 所有者の氏名が、似ているが違う文字になる
- そもそも「読み取れません」と返る

プロンプトを詳しくしても、出力例を足しても、当たり外れの傾向が変わりません。

## 原因

外れる方のPDFを開いて気づきました。**横向き、あるいは上下逆でスキャンされていました。**

現場でスキャンされた書類は向きが揃いません。複合機のADFに横向きで入れれば横向きで保存されるし、
綴じ方の都合で上下逆になることもあります。**人間は首を傾げれば読めるので、誰も問題視しません。**

モデルは回転した文字も「ある程度」読みます。だから**完全に失敗せず、部分的に外す**という、
いちばん厄介な壊れ方をしていました。エラーではないので気づけません。

## 直し方：読ませる前に、向きだけを直す

読み取りの前に、**回転角の判定だけを別工程にしました。**

```
スキャンPDF
  → ページを画像化
  → 【軽いモデル】回転角を判定（0 / 90 / 180 / 270 のいずれか）
  → 正立に回転
  → 【精度の高いモデル】本文を構造化して読み取り
```

ポイントは**モデルを使い分ける**ことです。

- **向きの判定は簡単な仕事**なので、いちばん軽いモデルで足ります。返すのは4択の数字だけ
- **本文の読み取りは間違えられない**ので、精度の高いモデルを使う

1工程増えますが、判定は4択なので出力トークンがほぼ要らず、負担はわずかです。
それで**本命の読み取りの入力品質が上がる**なら、確実に割に合います。

判定のプロンプトは、選択肢を絞り切るのが大事でした。

```
この画像を正立させるには何度回転させる必要がありますか。
0, 90, 180, 270 のいずれかの数字だけを返してください。説明は不要です。
```

## 前処理で直せるものを、プロンプトで直そうとしない

今回の教訓はこれに尽きます。

出力がおかしいとき、私たちはまずプロンプトを疑います。実際その方が多い。
ただ今回は**入力そのものが傾いていた**ので、指示をどれだけ詳しくしても限界がありました。

似た性質の前処理として、こういうものがあります。

- 傾き・向きの補正（今回）
- テキスト層の有無で経路を分ける（後述）
- 極端に大きい画像の縮小
- 白紙ページの除去

**どれも「モデルに投げる前の話」で、プロンプトの外側にあります。**

## おまけ：同じPDFでも中身は2種類ある

もう1つ、最初に分けておくべきだった分岐があります。

| 入力 | 実体 | 取り出し方 |
|---|---|---|
| テキスト層があるPDF | 文字データ | ライブラリでそのまま抽出（AI不要・速い・無料） |
| スキャンされたPDF | ただの画像 | 画像化してAIに読ませる |

拡張子が同じなので**同じものとして扱いがち**ですが、処理も費用も別物です。
テキスト層があるならAIを呼ぶ必要すらありません。まずそこを判定するだけで、
費用と時間がまとめて減ります。

## おまけ2：AIが使えないときは、黙って劣化させない

AIを呼べない環境向けに、正規表現で主要項目だけを拾うフォールバックを入れています。
ただし**画面に「要確認」の警告を出します。**

以前、フォールバックが静かに動いて半年気づかなかったことがあるので、
**代替に落ちたことは必ず見えるようにする**と決めています。

## まとめ

- **精度が出ないときは、プロンプトの前に入力を見る**
- 向きの判定のような「簡単で、間違えると全部が狂う」工程は、軽いモデルで前段に置く
- 完全に失敗せず**部分的に外す**壊れ方がいちばん危ない。エラーにならないので気づけない
