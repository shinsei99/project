業務チャットに常駐して質問に答えるAIを動かしています。窓口の一つが LINE です。

ある日から、**LINEに送っても答えが返らなくなりました**。ただし完全な無反応ではありません。

- 「調べています…🔎」という**受付の返事は届く**
- そのあとの**答えだけが来ない**

この見え方が、原因の特定を遅らせました。接続は生きているように見えるからです。

## 結論から

**月間の送信可能数（無料枠200通）を使い切っていました。**

LINE Messaging API で課金対象になるのは **push（こちらから任意のタイミングで送るもの）だけ**です。
**reply（受信直後の即時返信）は無料で、枠を消費しません。**

```
reply … 受信の webhook で受け取った reply_token に対する即時返信。無料・無制限
push  … userId 宛に任意のタイミングで送る。無料プランは月200通まで
```

この設計に、うちの実装がそのまま乗っていました。

- 受付の「調べています」は **reply** で返す（速いので）
- AIの回答は生成に時間がかかるので **push** で送る

つまり枠が切れると、**受付だけが届いて、答えだけが消える**。
利用者から見ると「途中まで反応するのに、答えが来ない」という、いちばん分かりにくい壊れ方になります。

実測では、**1日およそ50通**。200通の枠は**4日**で尽きていました。
しかも長文は分割して送るので、**1回の回答で複数通を消費**します。

```python
# 長文は 4800文字ごとに分割する。分割数だけ push の消費が増える
n = len(payload.get("messages") or [])
```

## 本当の問題は、無料枠ではなかった

枠が切れること自体は、想定できたはずの話です。問題は**気づけなかったこと**で、原因は2つありました。

### ① 失敗の理由を捨てていた

```python
# 直す前
def _post(url, payload):
    try:
        ...
        return True
    except Exception:
        return False      # ← 理由がここで消える
```

送信に失敗したら `False` が返るだけ。呼び出し側は「送れなかったんだな」としか分かりません。
`429 You have reached your monthly limit.` という**明確な答え**が本文に入っているのに、
それを読まずに捨てていました。

いまはこうしています。

```python
except urllib.error.HTTPError as e:
    body = e.read().decode("utf-8", "replace")
    # 429 = 送信可能メッセージ数の上限（月の無料枠切れ）
    if e.code == 429 or "monthly limit" in body.lower():
        _mark_quota_exhausted(body or "HTTP 429")
        _record_error("quota_exhausted", status=e.code, body=body)
    elif e.code in (401, 403):
        _record_error("auth", status=e.code, body=body)
    else:
        _record_error("http_error", status=e.code, body=body)
    print(f"[line] push 失敗 label={label or '-'} messages={n} status={e.code}", flush=True)
    return False
```

ポイントは3つです。

- **状態として持つ**（枠切れフラグ）。次の送信前に判断できる
- **最後のエラーを読み出せる**ようにする。管理画面から見える
- **呼び出し元の名前（label）を記録する**。どの機能が枠を食っているかを数えられる

### ② 障害を知らせる経路が、止まっているその経路だった

これがもっと悪い設計でした。
「LINEが止まった」ことを管理者に知らせる手段が、**LINE しかありませんでした**。

塞がっている道を通って「この道は塞がっています」と伝えることはできません。
いまは、枠切れを検知したら**別のチャットへ流す**ようにしています。

**通知の経路は、監視対象と別系統にする。** 当たり前のようで、一本化したときに真っ先に崩れるところです。

## 残量は、使い切る前に見る

LINE には残量を返すAPIがあります。

```
GET https://api.line.me/v2/bot/message/quota              … 枠の上限
GET https://api.line.me/v2/bot/message/quota/consumption  … 今月の消費数
```

上限のある資源は、**使い切ってから気づくのでは遅い**。
残りが一定を下回ったら知らせる、というだけの処理を入れておけば、この障害は起きませんでした。

同じ形は、無料枠のあるサービス全般にあります（メール送信数、APIのレート、ストレージ容量）。

## まとめ

- **課金対象と無料の経路が混在**していると、片方だけ止まって「半分動いている」ように見える
- 失敗は**理由まで残す**。`except: return False` は、いちばん高くつく2行
- **通知の経路は、監視対象と別系統**にする
- **残量は使い切る前に見る**

このとき利用者から見えていたのは「調べています…🔎」の一行だけです。
システムは動いていました。答えだけが、どこにも行かずに消えていました。
