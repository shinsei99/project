登記事項証明書（謄本）のPDFを読んで、不動産の書類に流し込むツールを作っています。
実案件で試したところ、**専有面積 72.59 ㎡ の部屋が、16.38 ㎡ として書き出されました**。

16.38 ㎡ は、同じ案件の**車庫**の面積です。

原因はPDFの読み取り精度ではなく、**複数枚の結果を1件にまとめる処理**でした。
`dict` を後勝ちでマージしていたので、あとに読んだ謄本が先に読んだ謄本を潰していたのです。

## 前提：区分所有の謄本は「一物件一枚」ではない

ここが実務側の前提で、コードだけ見ていると気づけない部分です。

区分所有建物（分譲マンション）では、**専有部分ごとに登記されます**。
駐車場が分譲されている物件だと、居宅と車庫はそれぞれ別の専有部分なので、
**謄本も別々に発行されます**。

```
touhon_1.pdf … 種類「居宅」   床面積 72.59 ㎡
touhon_2.pdf … 種類「車庫」   床面積 16.38 ㎡
```

つまり利用者は、**1つの取引に対して複数のPDFを投げてくる**のが正常な使い方です。

## 症状：入力の順番で結果が変わる

複数PDFの処理はこうなっていました。

```python
merged = json.loads(json.dumps(EMPTY))  # 空のスキーマ

for pdf in pdf_files:
    result = parse_one(pdf)             # 1枚ぶんを構造化
    _deep_merge(merged, result)         # ← 後勝ちで上書き

return merged
```

`_deep_merge` は「値が入っていれば上書きする」だけの素朴な実装です。
そのため、**渡された順番で結果が変わります**。

| 渡す順 | `建物.床面積` |
|---|---|
| 居宅 → 車庫 | **16.38 ㎡**（車庫に上書きされる） |
| 車庫 → 居宅 | 72.59 ㎡（たまたま正しい） |

このタイプのバグの厄介なところは、**例外が出ないこと**です。
面積の欄には数字が入っているし、書式も正しい。
おかしいと気づけるのは、その物件を知っている人間が見たときだけです。

家屋番号も同様に上書きされていました。

## 直し方1：まとめる順番を「附属 → 本体」にする

どちらが主たる建物かを決めて、**主たる建物を最後にマージ**すれば、
従来のキーには必ず本体が残ります。

```python
annexed = [(r, f) for r, f in records if _is_annex(r)]   # 車庫など
mains   = [(r, f) for r, f in records if not _is_annex(r)]

if not mains:                 # 車庫の謄本しか渡されなかったとき
    mains, annexed = annexed, []

for result, _fname in annexed + mains:   # ★附属が先、本体があと
    _deep_merge(merged, {k: v for k, v in result.items() if k != "物件種別"})
```

そのうえで、**潰した情報を捨てない**ようにします。
1枚＝1レコードの要約を別に持たせ、画面と書類の両方で使えるようにしました。

```python
merged["建物一覧"] = ([_summarize(r, f, False) for r, f in mains]
                    + [_summarize(r, f, True)  for r, f in annexed])
merged["附属建物一覧"] = [x for x in merged["建物一覧"] if x["区分"] == "附属"]
```

書類には家屋番号と種類を「①本体　②車庫」の形で連記し、床面積は本体のみを入れます。
**連記した文字列は別キーに持たせ、素の値は本体のまま**にしました。
既存のクロスチェック（謄本と契約書の突き合わせ）が連記文字列を比較して落ちるのを避けるためです。

## 直し方2：「どちらが車庫か」の判定順序

最初は建物の名称で判定していましたが、これは**本体を車庫と誤判定します**。

敷地権付き区分建物として読み取られた場合、名称の欄に入るのは
**一棟の建物の名称**（例：`○○レジデンスタワー`）です。
居宅も車庫も同じ文字列になるので、名称では区別できません。

判定は「種類」を第一に置きます。

```python
_ANNEX_WORDS = re.compile(r"車庫|駐車|駐輪|物置|倉庫|バイク|トランクルーム")

def _is_annex(result: dict) -> bool:
    kind = str((result.get("建物") or {}).get("種類") or "").strip()
    if kind:                                   # 表題部①種類が最優先
        return bool(_ANNEX_WORDS.search(kind))
    mans = result.get("マンション") or {}
    if _ANNEX_WORDS.search(str(mans.get("名称") or "")):
        return True
    return bool(_ANNEX_WORDS.search(str(mans.get("室番号") or "")))
```

所在や家屋番号では判定しません。
**建物名にたまたま「駐車場」が入っている物件で、本体を附属と誤判定するため**です。

## 直し方3：罫線が値として混入していたフォールバック

AI解析が使えない環境のために正規表現のフォールバックを置いていましたが、
ここも壊れていました。謄本は**罫線アートで組まれた表**です。

```
┃ ① 種 類 ┃ ② 構 造 ┃ ③ 床 面 積 ㎡ ┃ 原因及びその日付 ┃
```

`[^\n]+` で拾うと、**隣のセルや見出し行までまとめて**取り込みます。
実測では、種類の欄に `│ ② 構 造 │ ③ 床 面 積 ㎡ │ 原因及びその日付…` が入っていました。

対策は2つです。**罫線で切って最初のセルだけを取る**ことと、
**見出し語だったら捨てて次を探す**ことです。

```python
_BOX = re.compile(r"[┃│┏┓┗┛┠┨┯┷┳┻━─┼｜]")
_HEADING = re.compile(r"種\s*類|構\s*造|床\s*面\s*積|地\s*積|原因及び|その日付|"
                      r"登記の日付|表\s*題\s*部|権\s*利\s*部|順位番号|受付年月日")

def _cell(value: str) -> str:
    v = _BOX.split(str(value or ""))[0].strip().strip("　 ・:：")
    return "" if (not v or _HEADING.search(v)) else v

def grab(pattern):
    # re.search で打ち切らない。見出し行が先に当たることがある
    for m in re.finditer(pattern, text):
        v = _cell(m.group(1))
        if v:
            return v
    return ""
```

`re.search` で1件目に決め打ちすると、**見出しを拾って終わり**になります。
`finditer` で回して、中身のある値が出るまで進めるのが要点でした。

## 確認したこと

- 車庫を先に渡しても後に渡しても、専有面積は **72.59 ㎡**（修正前は 16.38 ㎡）
- 建物名に「駐車場」を含む物件で、本体が附属と誤判定されないこと
- この解析部分を共用しているもう一つのアプリ（媒介契約書の作成）の動作確認が通ること

## 最後に踏んだ罠：常駐アプリは古いコードのまま動く

この解析部分は、2つのStreamlitアプリが**同じファイルを読む共有モジュール**です。
修正を反映したのに、常駐させている側だけ古い動きのままでした。

Streamlitはスクリプトを再実行しますが、**すでに `import` 済みのモジュールは入れ替えません**。
ブラウザを開き直しても直りません。プロセスの再起動が要ります。

共有モジュールを直したら、**それを読んでいる常駐プロセスを再起動するまでが1つの作業**です。

## まとめ

- 複数の入力を1件にまとめる処理は、**順番で結果が変わっていないか**を疑う
- 上書きで消える値がある設計なら、**消えた側を残す置き場**を先に用意する
- 「どれが主か」の判定は、**業務上いちばん正確な欄**から順に見る（今回は登記の種類）
- 罫線で組まれた帳票を正規表現で読むときは、**セル境界で切ってから**評価する

例外が飛ばず、書式も整っていて、数字だけが違う。
このタイプの不具合は、実際の案件で人が見るまで見つかりません。
実データで一度通すことが、いちばん安いテストでした。
