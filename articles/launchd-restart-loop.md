社内向けに常駐させていたAPIサーバーが、**常駐登録されているのに応答しませんでした。**

原因はポート番号の重複です。それ自体は珍しくありませんが、
**自動再起動の設定が、その失敗を完全に隠していた**のが本題です。

## 症状

- 常駐サービスとしては「登録済み」で、プロセス一覧にも存在する
- なのにブラウザからもcurlからも応答しない
- エラー通知は何も出ていない

ログを見て分かりました。**起動 → 即クラッシュ → 自動再起動**をずっと繰り返していました。

```
Error: listen EADDRINUSE: address already in use :::8519
```

## 原因

そのポートは、別のアプリが先に使っていました。後から起動した側は必ず失敗します。

そこに `KeepAlive`（落ちたら再起動する設定）が効いていました。

```xml
<key>KeepAlive</key>
<true/>
```

**KeepAlive は「落ちた」と「起動できていない」を区別しません。** 結果として
「常に起動を試みている＝プロセスは存在する」状態になり、外からは動いているように見えます。
**自動再起動は可用性のための仕組みですが、同時に失敗を隠す装置でもあります。**

## 直し方

まず、実際に何が待ち受けているかを見ます。

```bash
lsof -nP -iTCP:8519 -sTCP:LISTEN
```

出力の見方が重要です。

- `127.0.0.1:8519` … ローカルのみ
- `*:8519` … **全インターフェースに公開**

空きポートへ移して再ビルドしたら解決しました。あわせて**ポート割り当ての一覧表**を作り、
新しいアプリはそこを見てから番号を決める運用にしました。

実は今回、**誰かが途中まで直した痕跡**（未コミットの変更で別の番号に変えてある）が
残っていました。ところがその番号も別アプリ用に予約済みで、結局また衝突する状態でした。
一覧表が無いと、直したつもりが次の衝突を作ります。

## おまけ：「指定しなければローカル限定」ではなかった

同じ点検で、もっと悪いものが見つかりました。

**待ち受けアドレスを指定していないサービスが、社内ネットワーク全体に公開されていました。**
コードのコメントには「ローカル」と書いてありましたが、**使っていたフレームワークの既定値が
全公開側**でした。Streamlit の `--server.address` を省略すると `0.0.0.0` になります。

```bash
# 明示する。省略した時の既定値を覚えている前提にしない
streamlit run app.py --server.address 127.0.0.1 --server.port 8527
```

個人情報を含むアプリがこの状態だったので、全アプリで待ち受けアドレスを明示しました。

## 教訓

- **プロセスが存在することは、動いていることの証明にならない。** 実際に叩いて確かめる
- 自動再起動を入れるなら、**再起動の回数が増えたことに気づける仕組み**（ログの確認・ヘルスチェック）を一緒に入れる
- **既定値は覚えておくものではなく、書いておくもの**。特に公開範囲に関わる設定は明示する

**エラーは出ていました。** 誰も見ていなかっただけです。
