写真から電線を消すツールを作っていて、**「消去エンジンの品質が低いから使えない」と判断して
半年止めていた**ことがあります。

再開して調べたら、そのエンジンは**一度も動いていませんでした。**

同じ踏み方をする人がいそうなので、症状と原因と直し方を書きます。

## 症状

物件写真から電線を消すと、跡が茶色く滲む。輪郭がぼやけ、実用にならない。

エラーは出ません。処理は最後まで走り、それらしい画像が返ってきます。**ただ品質が低いだけ。**
だから「このアルゴリズムでは無理」という結論になり、開発が止まりました。

## 原因

コードはこうなっていました。

```python
def inpaint_lama(image, mask):
    try:
        from simple_lama_inpainting import SimpleLama
        # ... 本命の処理
    except ImportError:
        # 入っていなければ OpenCV で代替
        return cv2.inpaint(image, mask, 3, cv2.INPAINT_TELEA)
```

一見すると親切なフォールバックです。問題は **`simple_lama_inpainting` が
`requirements.txt` に一度も書かれていなかった**こと。

つまり:

1. `import` は**毎回**失敗する
2. 例外は握り潰され、静かに `cv2.inpaint` が走る
3. OpenCV の TELEA は細い線の除去が苦手で、周囲の色を引き伸ばす → **茶色く滲む**
4. エラーが出ないので、誰も「本命が動いていない」と気づかない

**アルゴリズム選定の問題ではなく、エンジンが最初から入っていなかった**というだけでした。

## 直し方

依存関係に足す。それだけです。

```diff
# requirements.txt
+ simple-lama-inpainting
```

**実測: 1600×1067 の電線消去が CPU で約4秒。** 跡もほぼ分かりません。
半年ぶんの停滞が、1行で解けました。

## 本当の教訓は「暗黙のフォールバック」

直したのは1行ですが、危なかったのは**失敗を握り潰した設計**の方です。

フォールバックは「動き続けること」を優先する仕組みですが、**動き続けた結果、
品質が下がっていることに誰も気づけない**状態を作ります。今回はそれが半年続きました。

最低限、落ちたことは分かるようにしておくべきでした。

```python
try:
    from simple_lama_inpainting import SimpleLama
except ImportError as e:
    logger.warning("LaMa が読み込めません。簡易処理に切り替えます: %s", e)
    # 画面にも「簡易処理で動作中」と出す
```

「静かに劣化する」のが最悪です。**動かないなら止まってくれた方がマシ**でした。

## おまけ: Intel Mac は torch 2.2.2 で固定

同じアプリで踏んだもう1つの罠です。

`torch` は **2.2.2 が macOS x86_64 向けの最終ビルド**で、2.3 以降は arm64 のホイールしか
公開されていません。Intel Mac では新しい版を入れようとして必ず失敗します。

```txt
# requirements.txt
torch==2.2.2
```

arm64 の機体でも 2.2.2 で問題なく動いたので、両対応にするならここで固定するのが確実でした。

## おまけ2: 選択モデルは「大きい＝広く取れる」ではない

クリックした物体の輪郭を取るのに Segment Anything を使っています。モデルを変えて実測しました。

軽バンを1クリックした場合:

| モデル | 選択範囲 | 所要 | 結果 |
|---|---|---|---|
| mobile_sam | 14.2% | 1.8秒 | 輪郭がギザギザで、**車体の外へはみ出す** |
| vit_b | 5.6% | 24.1秒 | **スライドドア1枚**を境界正確に選択 |

数字だけ見ると「軽い方が広く取れて有利」に見えますが、逆でした。
大きいモデルは**意味のまとまりで正確に切る**方向に効きます。車を丸ごと消したいなら、
vit_b で追加クリックする方が結局きれいでした。
