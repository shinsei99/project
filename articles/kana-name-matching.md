家賃の入金消込を自動化しています。銀行からダウンロードした入金データと、こちらの入金一覧Excelを
突き合わせて、入金済み・未入金・金額ズレに仕分けるだけの道具です。

これを別のPCで動かしたら、**未突合の件数だけが増えました**。エラーは出ません。画面も普通に出ます。
落ちないので、気づくまでに時間がかかりました。

原因は、**漢字をカナに変換するライブラリを入れ忘れていたこと**です。
無いと例外で落ちるのではなく、**照合の候補が減って、一致率だけが静かに下がる**作りになっていました。

## 何を突き合わせているか

銀行の入金データに載っている名義は**カナ**です。

```
2026/08/05  振込  ﾀﾞｲｷﾖｳ ﾀﾛｳ  82,000
```

一方、こちらの入金一覧Excelに入っている契約者名は**漢字**です。

```
101号室  大京 太郎  82,000
```

文字種が違うので、そのままでは一文字も一致しません。そこで、契約者名から**カナの候補**を作って、
その集合に銀行側の名義が入っているかで判定しています。

```python
def _kana_candidates(tenant: str, tenant_key: str,
                     name_mapping: Dict[str, Set[str]]) -> Set[str]:
    """契約者名に対応する、正規化済みカナ候補の集合を返す"""
    candidates: Set[str] = set()
    # ① 人が作った対応表（旧姓・法人格の有無・家族名義などはここで吸収する）
    candidates.update(name_mapping.get(tenant_key, set()))
    # ② 漢字からの自動変換
    if HAS_PYKAKASI:
        kana = kanji_to_kana(tenant)
        if kana:
            candidates.add(kana)
    # ③ 契約者名そのもののカナ正規化（外国人名・カナ表記の法人向け）
    candidates.add(normalize_kana(tenant))
    candidates.discard('')
    return candidates
```

候補は3経路あります。**このうち②だけが、外部ライブラリに依存しています。**

## 依存が無いときに、何が起きたか

```python
try:
    import pykakasi
    _kks = pykakasi.kakasi()
    HAS_PYKAKASI = True
except ImportError:
    HAS_PYKAKASI = False


def kanji_to_kana(text: str) -> str:
    if not HAS_PYKAKASI or not text:
        return ''          # ← ここ
    ...
```

`ImportError` を握って、変換関数は**空文字を返して先へ進みます**。
呼び出し側は `if kana:` で弾くので、候補が1つ減るだけです。例外も警告も出ません。

結果として起きることは、こうです。

| 契約者名の登録 | 依存あり | 依存なし |
|---|---|---|
| カナ表記（法人・外国人名） | 当たる | 当たる（③が効く） |
| 対応表に登録済み | 当たる | 当たる（①が効く） |
| **漢字のみ・対応表に無い** | **当たる（②）** | **未突合になる** |

つまり、**新しく入った契約者から順に当たらなくなる**。既存の契約者は対応表に載っているので当たります。
このズレ方がやっかいで、「前は動いていたのに」という形では現れません。

## 「落とす」か「劣化を告知する」か

任意依存の扱いは、実質この3つです。

1. **落とす** — `import` を必須にして、無ければ起動しない
2. **劣化を告知する** — 動かすが、性能が落ちていることを利用者に見せる
3. **機能を隠す** — その機能に依存する画面ごと出さない

この道具では**2**を選びました。消込そのものは対応表と手作業でも回るので、
月末に止まるほうが困るからです。ただし、**黙って劣化させない**。

```python
from match_payments import HAS_PYKAKASI

# 漢字→カナ変換が使えないと、突合の候補が減って黙って一致率が下がる。
# 落ちないので気づけない。画面に出して分かるようにする。
if not HAS_PYKAKASI:
    st.warning(
        "**pykakasi が入っていないため、漢字の契約者名をカナに変換できません。**\n\n"
        "動作はしますが、突合の候補が減るぶん**一致率が下がります**（エラーにはなりません）。"
        "`pip install -r requirements.txt` で導入してください。"
    )
```

あわせて2つ。

**requirements には理由を書きました。** 「無くても動く」ものほど、次に読む人が外します。

```txt
streamlit
openpyxl
# 漢字の契約者名をカナに変換して突合の候補を作る。
# 無くても動くが**警告なしに突合率が落ちる**ので必須扱いにする。
pykakasi
```

**データ側にも痕跡を残しました。** 対応表へ新しい契約者を自動追加するとき、
カナを自動で入れられたのか、人が埋める必要があるのかを行ごとに記録します。

```python
candidate = kanji_to_kana(rec['tenant']) if HAS_PYKAKASI else ''
existing_rows.append({
    'kanji_name': rec['tenant'],
    'bank_kana':  candidate,
    'room':       str(rec.get('room', '')),
    'note':       'auto' if candidate else 'manual required',
})
```

こうしておくと、**空欄の理由があとから分かります**。
「まだ埋めていない」のか「そのとき変換が使えなかった」のかは、見た目では区別がつきません。

## 一般化すると

`try: import ... except ImportError: フラグ = False` は普通のパターンです。問題はその後で、

- **落ちない代わりに、何が悪くなるのか**
- **それは利用者から見えるのか**

この2つを決めていないと、「動いてはいる」という状態がいちばん長く続きます。
落ちるバグは、遅くとも次の実行で分かります。**性能が落ちるだけのバグは、誰かが数えるまで分かりません。**

同じ形は、機能検出を伴うところに広く出ます。OCRエンジン、画像処理の高速化ライブラリ、
形態素解析、地図のジオコーダ。どれも「無ければ精度が落ちるだけ」で済んでしまうものです。

判定はこうしています。

- **結果の正しさに関わる依存** → 必須にするか、使えないことを画面に出す
- **速さにしか関わらない依存** → ログに1行だけ残す

一致率は、正しさに関わります。だから画面に出しました。
