社内向けのアプリを30本ほど、Mac 1台に常時起動させています。
その運用で、**コードは直っているのに、動いているものが古い**という事故を、同じ月に4回、別々の原因で踏みました。

4つとも、**エラーは出ません**。コミットもされている。ログも正常。それでも古い。
確認の手順を持っていないと気づけない類のものなので、まとめて書きます。

## ① 起動スクリプトが、ビルドを飛ばしていた

エディタ画面（Vite + React）を常時起動させていました。機能を足して、動作確認もして、コミットした。
数日後、社内から「保存ボタンが無い」と言われました。

原因は、起動スクリプトのこの分岐です。

```bash
# 直す前
if [ ! -d dist ]; then
  npm run build
fi
node server.js
```

`dist` が在れば作り直さない。開発中は速くて助かりますが、
常時起動の側は**3週間前の `dist` を配り続けます**。

```
madori-tracer(editor): 起動時に必ず再ビルド（古いdistを配信し続ける不具合を修正）

run.shが「distが在れば再ビルドしない」作りで、保存/読込機能の追加後も
7/23の旧distを常時起動が配信し続けていた。毎回npm run buildする。
```

同じ作りの別アプリでも、**同じ事故**が起きていました。書いた人が同じなので、当然といえば当然です。

**直し方**: 起動のたびに必ずビルドする。数十秒の遅さと、古い画面を配る事故は釣り合いません。

## ② `launchctl kickstart -k` は plist を読み直さない

これがいちばん気づきにくい形でした。

待ち受けアドレスを `0.0.0.0`（LANに出る）から `127.0.0.1` に変えたくて、plist を書き換え、
`launchctl kickstart -k` で再起動しました。プロセス番号は変わります。**でも待ち受けは変わりません。**

```
$ lsof -nP -iTCP:8518 -sTCP:LISTEN
python3  91234  ...  TCP *:8518 (LISTEN)      # ← *:  のまま
```

`launchctl print` で見ると、引数が `0.0.0.0` のまま残っていました。

**`kickstart -k` は、ロード済みの定義でプロセスを起こし直すだけで、ディスク上の plist を読み直しません。**
だから、**コードだけ直した（引数は同じ）ときは効く**が、**引数を変えたときは効かない**。
プロセス番号が変わるので「再起動した」と思ってしまうところが、この事故のたちの悪さです。

```bash
# 引数を変えたときは、外して入れ直す
launchctl bootout   gui/$(id -u)/<label>
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/<label>.plist
launchctl print gui/$(id -u)/<label> | grep -A2 server.address   # 反映を確認
lsof -nP -iTCP:<port> -sTCP:LISTEN                               # 待ち受けを確認
```

## ③ 起動スクリプトを直しても、plist が別のコマンドを叩いていた

②と逆向きの話です。

`run.sh` は前から `--server.address 127.0.0.1` で正しく書いてありました。
それでも LAN に出ていたので調べたら、**plist が `run.sh` を経由していませんでした**。

```xml
<key>ProgramArguments</key>
<array>
  <string>/usr/bin/python3</string>
  <string>-m</string><string>streamlit</string><string>run</string>
  <string>app.py</string>
  <!-- ここに --server.address が無い＝既定の 0.0.0.0 -->
</array>
```

`run.sh` は手動起動のときにしか使われていなかった、という話でした。

**教訓**: 「起動スクリプトを直した」は、常駐に対する何の保証にもなりません。
**本番が何を実行しているかは、定義のほうを読んで確かめる。**

## ④ 常駐は、読み込み済みのモジュールを入れ替えない

複数のアプリが同じ共有モジュール（住所の正規化）を読んでいます。そこを直して、画面で確認したら、
**古い挙動のまま**でした。

Streamlit はブラウザを更新するたびにスクリプトを頭から実行し直します。
「毎回読み直している」ように見えるのですが、**`import` 済みのモジュールは入れ替わりません**。
プロセスが生きている限り、最初に読み込まれたものが使われ続けます。

**直したら、それを読んでいる常駐を全部再起動するまでが1セット**です。
共有モジュールに手を入れたときは、影響範囲のアプリを一覧にして落とし直します。

## 4つに共通していること

| # | 直したもの | 動いていた古いもの | 気づき方 |
|---|---|---|---|
| ① | ソース | ビルド成果物 | 成果物の生成時刻を見る |
| ② | plist | ロード済みの定義 | `launchctl print` と `lsof` |
| ③ | 起動スクリプト | plist が直接叩くコマンド | plist の中身を読む |
| ④ | 共有モジュール | プロセスが抱えた import | 再起動してから確認する |

どれも、**「直した」の対象と、「動いている」の実体がズレている**という一つの形です。
そしてズレている間、システムは正常に見えます。エラーは出ません。

なので、直したあとに見るものを決めておくしかありません。

- 成果物の**生成時刻**（`ls -l dist`）
- 実際の**待ち受け**（`lsof -nP -iTCP:<port> -sTCP:LISTEN`）
- 実際の**引数**（`launchctl print`）
- **再起動してから**の動作確認

「直しました」で終わらせず、**そのうちのどれかを1つ見る**。
これだけで、この4つは全部その場で捕まえられます。
