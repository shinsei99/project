毎晩1回、書類フォルダを走査してスキャンPDFをAIに読ませ、全文検索の索引に載せる処理を
常駐（launchd）から流しています。ある朝、その晩の成果が **0件** でした。

ログにはこう出ていました。

```
[2026-08-28 01:00:21] 終了 0.3分 / 中断理由: 連続失敗 5 件（定額枠切れ・環境異常の可能性）
OCR取込 0 / 認識なし 5 / 失敗 0 / 追加チャンク 0
```

「定額枠切れの可能性」と書いてあったので、**枠切れだと判断しました。これが間違いでした。**

## 手で流すと、普通に読める

読めなかった5件を、朝にターミナルから同じコマンドで流しました。

```
OCR取込 3 / 追加チャンク 59
OCR取込 2 / 追加チャンク 29
```

5件とも読めました。**同じコード・同じ書類・同じユーザー**で、結果が違う。
違うのは「どこから起動されたか」だけです。

## 原因：launchd から起動するとPATHが空

失敗の中身はこの1行でした。

```
SessionEnd hook [node ".../session-end-cleanup.mjs"] failed:
/bin/sh: node: command not found
```

`launchctl getenv PATH` は空文字を返します。ログインシェルの `PATH` は
`~/.zshrc` などが作るもので、**launchd から起動されたプロセスには渡りません。**

問題は、見つからなかったコマンドが**本体ではなかった**ことです。

- 本体（AIのCLI）は絶対パスで呼んでいるので、起動できている
- 応答も返ってきている
- ただし**終了時のフック**が別の実行環境（node）をPATHから探し、見つけられずに失敗した
- その結果、CLI全体が**非ゼロで終了した**

呼び出し側は、こう書いていました。

```python
proc = subprocess.run(cmd, capture_output=True, text=True, timeout=timeout)
if proc.returncode != 0:
    raise ClaudeError(f"claude 失敗（code={proc.returncode}）: {proc.stderr.strip()[:500]}")
```

**終了コードは「本体の成否」ではなく「プロセス全体の成否」です。**
終了フック・プラグイン・後片付けの失敗も、同じ1つの数字に混ざります。
応答は取れていたのに、呼び出し側からは「AIが落ちた」に見えていました。

そして、**手で流すと再現しません。** ここが一番厄介でした。

## 直し方：起動スクリプトの先頭でPATHを書く

```bash
#!/bin/bash
set -u
# launchd から起動されると PATH が空になり、CLI の終了フックが呼ぶ node が
# 見つからず、応答していても非ゼロ終了になる。手で流すと再現しない。
export PATH="/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin"
```

plist の `EnvironmentVariables` ではなく、**スクリプト側**に置きました。

- plist を触ると、引数を変えるたびに `bootout` → `bootstrap` の入れ直しが要る
  （`launchctl kickstart -k` はロード済みの定義で再起動するだけで、plistを読み直さない）
- スクリプトはリポジトリに入るので、もう1台のマシンにもそのまま渡る
- 手で流したときと**同じ経路**になるので、「手ならできる」の差が消える

### ついでに：継ぎ足しは効かない

よく見る書き方ですが、launchd 下ではこうなります。

```bash
export PATH="/opt/homebrew/bin:/usr/local/bin:$PATH"
# launchd 下では $PATH が空 → "/opt/homebrew/bin:/usr/local/bin:"
#   → /usr/bin も /bin も入らない（git も sed も見つからない）
#   → さらに末尾のコロンは空要素＝カレントディレクトリの意味になる
```

継ぎ足す前提を置かず、**必要なディレクトリを全部書き切る**ほうが安全です。

### 検証

PATHを通さずにCLIを呼ぶとフックのエラーが出て、通すと出ないことを確認したうえで、
**常駐経由で2件流して2件とも成功**（29チャンク）しました。
前の晩は同じ経路で0件だったので、これで原因が確定しています。

## 直したのはPATHだけではない

この障害は、**別の2つのバグが重なって初めて「全滅」になりました。**

### 1. 推測をログに断定形で書いていた

```python
stopped = f"claude が連続 {streak} 回こけた（定額枠切れ・環境異常の可能性）。"
```

失敗の中身を残さずに、**書いた人の推測だけ**を残していました。
翌朝これを読んだ人（自分です）は、そのまま枠切れだと判断して半日ずらしました。
いまは、返ってきたエラーの先頭をそのまま残しています。推測は、事実の後ろに置く。

### 2. 「AIが落ちた」と「文字が無い書類」を区別していなかった

もっと悪かったのがこちらです。旧コードは、呼び出しが失敗したとき**空のリスト**を返していました。
呼び出し側から見ると、それは「この書類には文字が入っていない」と同じ形です。

```python
except ClaudeError:
    return []          # ← 呼び出し側は「文字が無い」と解釈し、見送りに登録する
```

見送りに入った書類は、翌晩から**対象外**になります。
つまり、AIが落ちていた晩に当たったというだけの理由で、その書類は**二度と読まれません。**

```python
class OcrUnavailable(Exception):
    """OCRの土台が使えなかった。**書類に文字が無いのとは別物**。"""

except ClaudeError as e:
    raise OcrUnavailable(str(e)) from e
```

呼び出し側では、この例外だけを「土台の異常」として数えます。

```python
ABORT_AFTER_BACKEND_FAILS = 3   # 連続でこの回数こけたら、その晩は諦める

except OcrUnavailable:
    failed += 1
    streak += 1          # 中断の判定に数える。ただし見送りには入れない
```

逆に「本当に文字が取れなかった」は、中断の判定に**数えません**。
落ちているときだけ止まり、単に読めない書類が続いただけでは止まらない、という区別です。

## まとめ

- launchd から起動されたプロセスは **PATH が空**。ログインシェルの設定は渡らない
- 絶対パスで本体を呼んでいても、**その本体が内部で呼ぶコマンド**は PATH を使う
- 終了コードは本体の成否ではない。**終了処理の失敗も同じ数字に混ざる**
- 手で流すと再現しない障害は、まず「起動された経路の違い」を疑う
- ログに推測を断定形で書くと、翌朝の自分が誤診する
- 一時的な障害を「恒久的な除外」に変換する経路があると、被害が翌日以降まで残る

最後の項目がいちばん怖い点でした。PATHは1行で直りますが、
除外リストに入った書類は**誰も気づかないまま**索引から消え続けます。
